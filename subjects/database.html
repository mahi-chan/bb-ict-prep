    1. Fundamentals and three-schema architecture

    A database is a structured collection of related data managed by a DBMS (Database Management System). Before DBMS, applications used flat files — each program maintained its own data, leading to redundancy, inconsistency and no concurrent access. The DBMS solves all three by sitting between the application and the data.

    FeatureFile systemDBMS
    Data redundancyHigh — each program stores its own copyMinimal — single store, shared access
    Data consistencyHard to maintainEnforced by integrity constraints
    Concurrent accessNo built-in supportLocking + transaction isolation
    SecurityOS-level file permissions onlyFine-grained (table/row/column)
    Crash recoveryManualAutomatic via logging/checkpoints
    Data independenceNone — structure changes break programsLogical and physical independence
    InstanceThe data stored at a particular moment — a snapshot of the database.
    SchemaThe structure — table names, columns, types, constraints. Changes rarely.
    Data modelsRelational (tables), hierarchical (tree), network (graph), object-oriented, document. Exam: relational is the focus.

    2. ER modelling

    An Entity-Relationship diagram is the first design step — it captures entities (things), attributes (properties) and relationships (connections) before any table is created. The exam asks you to draw ER diagrams or convert them to tables.

    Attribute typesSimple (atomic), composite (sub-parts), derived (calculated), multivalued (multiple values), key (underlined).
    Cardinality1:1, 1:N, M:N. Determines how the relationship maps to tables.
    ParticipationTotal (double line — every entity must participate) vs partial (single line — optional).
    Weak entityHas no key of its own; depends on a strong entity (identifying relationship, double diamond). Example: Dependent of Employee.

    ER-to-relational mapping

    1:1Add the primary key of one side as a foreign key in the other (prefer the side with total participation).
    1:NAdd the primary key of the "1" side as a foreign key in the "N" side.
    M:NCreate a new table with the primary keys of both entities as a composite key. Relationship attributes go here.
    Weak entityCreate a table whose primary key = owner's PK + partial key. Add FK to the owner.

    3. Relational model and keys

    The relational model represents data as tables (relations). Each row is a tuple, each column is an attribute. The key system is how we identify rows and link tables.

    Running example — three tables 
    Student (SID, Name, Dept)
  (101, 'Rahim',  'CSE')
  (102, 'Karim',  'EEE')
  (103, 'Fatima', 'CSE')

Course (CID, Title, Credits)
  ('CS101', 'DBMS',    3)
  ('CS201', 'Algo',    3)
  ('EE101', 'Circuits',3)

Enrolment (SID, CID, Grade)
  (101, 'CS101', 'A')
  (101, 'CS201', 'B+')
  (102, 'CS101', 'A-')
  (103, 'EE101', 'B')
    Key typeDefinitionExample
    Super keyAny set of attributes that uniquely identifies a tuple{SID}, {SID, Name}, {SID, Dept}
    Candidate keyMinimal super key (remove any attribute and it stops being unique){SID}
    Primary keyThe chosen candidate keySID (underlined)
    Alternate keyCandidate keys not chosen as primaryIf Name were unique, it would be alternate
    Foreign keyAttribute referencing another table's primary keyEnrolment.SID → Student.SID
    Composite keyKey made of two or more attributesEnrolment: (SID, CID)
    Entity integrityPrimary key cannot be NULL — every row must be identifiable.
    Referential integrityA foreign key value must either be NULL or match an existing primary key in the referenced table.
    Domain constraintEach attribute value must belong to its declared domain (e.g. Grade must be a valid letter grade).

    4. Relational algebra

    Relational algebra is a procedural query language — you specify how to get the data step by step. Every SQL query is internally converted to a relational algebra expression by the query optimiser.

    σ (Select)Filter rows: σDept='CSE'(Student) → {Rahim, Fatima}
    π (Project)Pick columns: πName(Student) → {Rahim, Karim, Fatima}
    ∪ (Union)All rows from both (same schema). Duplicates removed.
    − (Difference)Rows in A but not in B.
    × (Cartesian)Every row of A paired with every row of B. |A| × |B| rows.
    ρ (Rename)Give a relation or attribute a new name.

    Joins

    Natural join — match on common attribute names 
    Student ⋈ Enrolment  (join on SID)
→ (101, 'Rahim', 'CSE', 'CS101', 'A')
  (101, 'Rahim', 'CSE', 'CS201', 'B+')
  (102, 'Karim', 'EEE', 'CS101', 'A-')
  (103, 'Fatima','CSE', 'EE101', 'B')
    Join types
    JoinKeepsUnmatched rows?
    Inner / NaturalOnly matching rowsDiscarded
    Left outerAll left + matching rightLeft kept, right filled with NULL
    Right outerMatching left + all rightRight kept, left filled with NULL
    Full outerAll from bothBoth sides filled with NULL

    5. SQL

    SQL is the declarative counterpart to relational algebra — you say what you want, the DBMS decides how to get it. The exam tests both reading and writing queries, using JOIN, GROUP BY, HAVING, subqueries and set operations.

    SQL sub-language categories
    CategoryCommandsPurpose
    DDLCREATE, ALTER, DROP, TRUNCATEDefine/modify structure
    DMLSELECT, INSERT, UPDATE, DELETEManipulate data
    DCLGRANT, REVOKEControl access
    TCLCOMMIT, ROLLBACK, SAVEPOINTTransaction control
    Query 1 — students in CSE who scored an A in any course 
    SELECT s.Name, e.CID, e.Grade
FROM   Student s
JOIN   Enrolment e ON s.SID = e.SID
WHERE  s.Dept = 'CSE' AND e.Grade = 'A';
    Rahim | CS101 | A
    Query 2 — count of enrolments per student, only those with 2+ 
    SELECT   s.Name, COUNT(*) AS cnt
FROM     Student s
JOIN     Enrolment e ON s.SID = e.SID
GROUP BY s.Name
HAVING   COUNT(*) >= 2;
    Rahim | 2
    WHERE vs HAVINGWHERE filters rows before grouping. HAVING filters groups after aggregation.
    Execution orderFROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
    SubqueryWHERE SID IN (SELECT SID FROM Enrolment WHERE Grade = 'A') — nested query returns a set.
    CorrelatedInner query references outer query: WHERE EXISTS (SELECT 1 FROM ... WHERE e.SID = s.SID). Re-evaluated for each outer row.

    6. Normalization

    Normalization removes redundancy by decomposing a table until each fact is stored exactly once. The process is driven by functional dependencies — if knowing X lets you determine Y, then X → Y is an FD.

    An unnormalised student-course table 
    StudentCourse (SID, SName, CID, CTitle, Credits, Grade)
  (101, 'Rahim', 'CS101', 'DBMS',  3, 'A')
  (101, 'Rahim', 'CS201', 'Algo',  3, 'B+')
  (102, 'Karim', 'CS101', 'DBMS',  3, 'A-')

FDs:
  SID → SName             (student name depends on SID only)
  CID → CTitle, Credits   (course info depends on CID only)
  SID, CID → Grade        (grade depends on both)
    Candidate key{SID, CID} — the only minimal set that determines all attributes (use attribute closure to verify).
    Normal forms — what each fixes
    NFRuleAnomaly removed
    1NFAll attributes are atomic (no repeating groups, no multivalued)Structural irregularity
    2NF1NF + no partial dependency (no non-key attribute depends on part of the composite key)Redundancy from partial keys
    3NF2NF + no transitive dependency (no non-key attribute depends on another non-key)Redundancy from indirect deps
    BCNFEvery determinant is a candidate key (stricter than 3NF)Remaining key-based anomalies

    Decomposition of the example

    Step-by-step normalization to 3NF 
    Original: StudentCourse (SID, SName, CID, CTitle, Credits, Grade)
Key: {SID, CID}

-- Partial dependencies violate 2NF:
--   SID → SName            (SID is part of key)
--   CID → CTitle, Credits  (CID is part of key)

Decompose → 2NF:
  Student    (SID, SName)
  Course     (CID, CTitle, Credits)
  Enrolment  (SID, CID, Grade)

-- No transitive dependencies remain → already in 3NF ✓
-- Every determinant is a candidate key → also in BCNF ✓
    Why normalize? In the original table, if we update Rahim's name, we must find and update every row with SID=101 — miss one and the data is inconsistent. After decomposition, Rahim's name lives in exactly one row in the Student table. One update, no risk.
    Armstrong's axiomsReflexivity: X ⊇ Y → X→Y. Augmentation: X→Y → XZ→YZ. Transitivity: X→Y ∧ Y→Z → X→Z.
    Attribute closureStart with a set X. Apply FDs to add everything X determines. If the closure X⁺ = all attributes, X is a super key.
    Lossless joinA decomposition is lossless if joining the pieces back gives exactly the original — no spurious tuples.

    7. Transactions and ACID

    A transaction is a logical unit of work — a sequence of operations that either all succeed or all fail. The classic example is a bank transfer: debit one account and credit another. If the system crashes between the two, the DBMS must undo the partial work.

    Transfer ৳5000 from account A to B 
    BEGIN TRANSACTION;
  UPDATE Account SET balance = balance - 5000 WHERE id = 'A';
  UPDATE Account SET balance = balance + 5000 WHERE id = 'B';
COMMIT;
    ACID properties
    PropertyMeaningEnforced by
    AtomicityAll or nothing — partial results are undoneLogging + rollback
    ConsistencyDatabase moves from one valid state to anotherConstraints + application logic
    IsolationConcurrent transactions don't interfereLocking / MVCC
    DurabilityOnce committed, data survives crashesWrite-ahead log + checkpoints

    Serializability

    ScheduleAn ordering of operations from multiple concurrent transactions.
    Serial scheduleTransactions execute one after another — always correct, but slow.
    Conflict serializableA schedule is CS if it can be transformed into a serial schedule by swapping non-conflicting operations. Test via a precedence graph — if acyclic, CS.
    ConflictTwo operations conflict if they are from different transactions, on the same data item, and at least one is a write.

    8. Concurrency control

    When multiple transactions run concurrently, the DBMS must prevent anomalies — lost updates, dirty reads, unrepeatable reads and phantom reads. The main mechanism is locking.

    Lock types
    LockAlso calledAllows concurrent
    Shared (S)Read lockOther S locks — yes. X lock — no.
    Exclusive (X)Write lockNothing — only the holder can access the item.
    Two-phase locking (2PL) — the standard protocol 
    Phase 1: Growing   — acquire locks, never release any.
Phase 2: Shrinking — release locks, never acquire new ones.

T1: lock-S(A), lock-X(B), read(A), write(B), unlock(A), unlock(B)
     ←——— growing ———→  ←——— shrinking ———→

2PL guarantees conflict-serializability.
    Strict 2PLHold all X locks until commit/abort. Prevents cascading rollbacks.
    Rigorous 2PLHold all locks (S and X) until commit/abort. Simplest, strictest.

    Deadlock

    Wait-dieOlder waits, younger aborts (dies). No younger-waits-for-older → no deadlock.
    Wound-waitOlder wounds (aborts) younger. Younger waits for older. Opposite policy.

    9. Recovery

    When a crash occurs, the DBMS must restore the database to a consistent state. The mechanism is write-ahead logging (WAL): before any change reaches the database, the log record is written to disk.

    Log records for the transfer example 
    [LSN 1] <T1, START>
[LSN 2] <T1, A, old=10000, new=5000>
[LSN 3] <T1, B, old=20000, new=25000>
[LSN 4] <T1, COMMIT>

If crash before LSN 4 → UNDO T1: restore A=10000, B=20000.
If crash after  LSN 4 → REDO T1: ensure A=5000, B=25000 on disk.
    UNDOReverse uncommitted changes using old values from the log. Needed for atomicity.
    REDORe-apply committed changes using new values from the log. Needed for durability.
    CheckpointA point where all committed data is flushed to disk. Recovery only needs to process log records after the last checkpoint.
    Shadow pagingAlternative to logging: maintain two page tables (current and shadow). On commit, swap pointers. No UNDO/REDO needed but poor for large DBs.

    10. Storage and indexing

    Without an index, finding a row requires scanning every page on disk — a full table scan. An index is a separate structure that maps search-key values to the disk location of the matching rows, just like a textbook index maps topics to page numbers.

    Index classification
    DimensionTypes
    OrderingPrimary (on ordering key of a sorted file), Clustering (on non-key ordering field), Secondary (on any field, file may be unsorted)
    DensityDense (one entry per record), Sparse (one entry per block)
    StructureB-tree, B+ tree, hash index

    B+ tree

    B-treeData pointers at every node (internal + leaf). Fewer levels but complex deletion.
    B+ treeData pointers only at leaves. Leaves linked → efficient range queries. This is what all real DBMS use.
    Lookup costO(logn N) where n is the order and N is the number of keys. Typically 3–4 disk reads even for millions of rows.

    11. RAID

    RAID (Redundant Array of Independent Disks) combines multiple physical disks to achieve higher performance, higher reliability, or both. The exam asks for level descriptions, usable capacity and fault tolerance.

    RAID levels — n = number of disks
    LevelTechniqueMin disksUsable capacityFault tolerance
    0Striping only2n × disk0 disks
    1Mirroring2n/2 × disk1 disk per pair
    5Striping + distributed parity3(n−1) × disk1 disk
    6Striping + double parity4(n−2) × disk2 disks
    10Mirrored stripes (1+0)4n/2 × disk1 per mirror pair
    Example6 disks × 1 TB each, RAID 5: usable = (6−1) × 1 = 5 TB. One disk can fail.
    RAID 10 same6 disks × 1 TB, RAID 10: usable = 6/2 × 1 = 3 TB. Better write performance than RAID 5.

    12. Triggers, views and programmability

    A trigger is a stored procedure that fires automatically when a specified event occurs on a table. The exam asks you to write simple triggers and to distinguish row-level from statement-level.

    Trigger — log every grade update 
    CREATE TRIGGER trg_grade_audit
AFTER UPDATE OF Grade ON Enrolment
FOR EACH ROW
BEGIN
    INSERT INTO AuditLog (SID, CID, OldGrade, NewGrade, ChangedAt)
    VALUES (OLD.SID, OLD.CID, OLD.Grade, NEW.Grade, CURRENT_TIMESTAMP);
END;
    Row-levelFOR EACH ROW — fires once per affected row. Has access to OLD and NEW row values.
    Statement-levelFOR EACH STATEMENT — fires once per SQL statement, regardless of rows affected.
    BEFORE vs AFTERBEFORE triggers can modify the new row before it is written. AFTER triggers see the final state.

    Views

    A view — a named query treated as a virtual table 
    CREATE VIEW CSE_Students AS
SELECT SID, Name FROM Student WHERE Dept = 'CSE';

-- Now: SELECT * FROM CSE_Students;
-- Returns: (101, 'Rahim'), (103, 'Fatima')
    Updatable?A view is updatable if it maps to a single base table with no aggregates, no DISTINCT, no GROUP BY, and includes the primary key.
    Materialized viewStores the result physically (like a cache). Must be refreshed when base data changes. Useful for expensive analytical queries.

    13. NoSQL, OLAP and CAP theorem

    Relational databases assume structured data with strong consistency. When data is unstructured, semi-structured, or distributed at massive scale, NoSQL databases trade some ACID guarantees for flexibility and performance.

    NoSQL data models
    ModelStructureExampleBest for
    Key-valueSimple key → value pairsRedis, DynamoDBCaching, sessions
    DocumentJSON/BSON documentsMongoDB, CouchDBContent management, catalogs
    Column-familyRows with variable columnsCassandra, HBaseTime series, analytics
    GraphNodes + edgesNeo4j, ArangoDBSocial networks, recommendations
    OLTP vs OLAP
    FeatureOLTPOLAP
    PurposeDay-to-day transactionsAnalysis and reporting
    OperationsINSERT, UPDATE, DELETEComplex SELECT, aggregations
    DesignNormalized (3NF/BCNF)Denormalized (star/snowflake)
    Response timeMillisecondsSeconds to minutes
    Data sizeCurrent data (GBs)Historical data (TBs)
    CAP theoremA distributed system can guarantee at most two of: Consistency, Availability, Partition tolerance. Since network partitions are inevitable, the real choice is CP (consistent but may reject requests) vs AP (available but may serve stale data).
    BASEBasically Available, Soft state, Eventually consistent. The NoSQL alternative to ACID — data converges over time.
    Star schemaCentral fact table (sales, transactions) surrounded by dimension tables (product, time, location). The standard OLAP design.

    S1 Explain the ACID properties with examples. past paper

    Consider a bank transfer of ৳5,000 from account A (balance ৳10,000) to account B (balance ৳20,000):

    AtomicityBoth the debit (A → ৳5,000) and credit (B → ৳25,000) must execute, or neither does. If the system crashes after the debit but before the credit, the DBMS rolls back the debit.
    ConsistencyThe sum A + B must remain ৳30,000 before and after. No constraint is violated — the database moves from one valid state to another.
    IsolationIf another transaction reads A and B while the transfer is in progress, it must not see the intermediate state (A debited, B not yet credited). It sees either the before or after state.
    DurabilityOnce the transfer commits, the new balances survive even if the server loses power immediately. The DBMS ensures this by flushing the log to disk before acknowledging the commit.

    S5 What is a trigger? Write a trigger that prevents inserting a student with GPA below 2.0. standard repeat

    S6 Explain RAID levels 0, 1, 5 and 10. If you have 8 disks of 500 GB each, calculate usable capacity for each level. standard repeat
    RAID 0Striping only. Usable = 8 × 500 GB = 4000 GB (4 TB). No fault tolerance.
    RAID 1Mirroring. Usable = 8/2 × 500 GB = 2000 GB (2 TB). Tolerates 1 disk failure per pair.
    RAID 5Striping + distributed parity. Usable = (8−1) × 500 GB = 3500 GB (3.5 TB). Tolerates 1 disk failure.
    RAID 10Mirrored stripes. Usable = 8/2 × 500 GB = 2000 GB (2 TB). Tolerates 1 per mirror pair. Best write performance.
    S7 Write SQL queries: (a) find all students in CSE department, (b) find the average grade per course, (c) find courses with more than 5 enrolments. standard repeat 
    -- (a) Students in CSE
SELECT * FROM Student WHERE Dept = 'CSE';

-- (b) Average grade per course (assuming numeric grades)
SELECT   CID, AVG(Grade) AS avg_grade
FROM     Enrolment
GROUP BY CID;

-- (c) Courses with more than 5 enrolments

FROM     Enrolment

    (a)Simple SELECT + WHERE filter. No join needed — all data is in the Student table.

    S8 Differentiate between B-tree and B+ tree indexing. standard repeat
    FeatureB-treeB+ tree
    Data pointersAt internal and leaf nodesOnly at leaf nodes
    Leaf linkageNo linked listLeaves are linked (doubly)
    Duplicate keysNo (key appears once)Separator keys copied in internal nodes

    Key insight: B+ tree's higher fan-out means fewer tree levels — a B+ tree with order 200 and 10 million keys needs only 3 levels (200 → 40,000 → 8,000,000). This means at most 3 disk reads per lookup.

    S9 What is deadlock in a DBMS? How is it detected and prevented? past paper

    A deadlock occurs when two or more transactions are waiting for each other to release locks, forming a cycle — none can proceed.

    Deadlock scenario 
    T1: lock-X(A), waiting for lock-X(B)
T2: lock-X(B), waiting for lock-X(A)
→ Neither can proceed. Deadlock.
    DetectionBuild a wait-for graph periodically. If it contains a cycle → deadlock. Abort one transaction (the victim — typically the youngest or least-work-done).
    Prevention (wait-die)Older transaction waits; younger one is aborted (dies). No younger-waits-for-older edges → no cycles.
    Prevention (wound-wait)Older transaction "wounds" (forces abort of) younger one. Younger transaction waits for older. No cycles.
    TimeoutSimple alternative: if a transaction waits longer than a threshold, abort it. May abort non-deadlocked transactions unnecessarily.

    P1 Given the relation R(A, B, C, D, E) with FDs: A→B, BC→D, D→E, find all candidate keys.
    Step 1Attributes that never appear on the RHS of any FD: {A, C}. These must be in every candidate key.
    Step 2Compute {A, C}⁺: A→B gives {A, B, C}. BC→D gives {A, B, C, D}. D→E gives {A, B, C, D, E}. Closure = all attributes. ✓
    Result{A, C} is a candidate key (and the only one, since both A and C must be included and their closure already covers everything).
    P2 Write a SQL query to find the second highest salary from an Employee table.
    Method 1 — subquery 
    SELECT MAX(Salary) AS SecondHighest
FROM   Employee
WHERE  Salary < (SELECT MAX(Salary) FROM Employee);
    Method 2 — LIMIT/OFFSET 
    SELECT DISTINCT Salary
FROM   Employee
ORDER BY Salary DESC
LIMIT 1 OFFSET 1;
    Method 1Inner query finds the max salary. Outer query finds the max among the rest — which is the second highest.
    Method 2DISTINCT removes duplicates, ORDER BY DESC sorts highest first, OFFSET 1 skips the top salary, LIMIT 1 picks the next.

    P4 Compare the four types of SQL joins with example output.
    Setup — two tiny tables 
    Student: (1, 'Rahim'), (2, 'Karim'), (3, 'Fatima')
Enrolment: (1, 'CS101'), (2, 'CS101'), (4, 'EE101')
-- Note: Student 3 has no enrolment; Enrolment has SID=4 with no student
    -- INNER JOIN: only matching rows
SELECT * FROM Student s INNER JOIN Enrolment e ON s.SID = e.SID;
→ (1, Rahim, CS101), (2, Karim, CS101)

-- LEFT JOIN: all left + matching right (NULLs for no match)
SELECT * FROM Student s LEFT JOIN Enrolment e ON s.SID = e.SID;
→ (1, Rahim, CS101), (2, Karim, CS101), (3, Fatima, NULL)

-- RIGHT JOIN: matching left + all right
SELECT * FROM Student s RIGHT JOIN Enrolment e ON s.SID = e.SID;
→ (1, Rahim, CS101), (2, Karim, CS101), (NULL, NULL, EE101)

    P5 Explain the CAP theorem. Which guarantee does each of the following databases prioritize: MongoDB, Cassandra, MySQL?
    C (Consistency)Every read returns the most recent write. All nodes see the same data at the same time.
    A (Availability)Every request gets a response (success or failure), even during failures.
    P (Partition tolerance)System continues to operate despite network partitions between nodes.

    Since network partitions are unavoidable in distributed systems, the real trade-off is between C and A:

    DatabaseCAP choiceBehaviour during partition
    MySQL (single node)CANo partition to tolerate — single node gives both C and A
    MongoDBCPElects a new primary → consistent but temporarily unavailable during election
    CassandraAPAll nodes accept writes → available but may serve stale data (eventual consistency)

    P8 Explain conflict serializability. Is the following schedule conflict-serializable?
    T1: R(A), W(A), R(B), W(B)
    T2: R(A), W(A), R(B), W(B)
    Schedule: R1(A), R2(A), W1(A), W2(A), R1(B), R2(B), W1(B), W2(B)
    Step 1 — find conflicting pairs 
    On item A:
  R1(A) vs W2(A): T1 before T2 → T1 → T2
  R2(A) vs W1(A): T2 before T1 → T2 → T1
  W1(A) vs W2(A): T1 before T2 → T1 → T2

On item B:
  R1(B) vs W2(B): T1 → T2
  R2(B) vs W1(B): T2 → T1
  W1(B) vs W2(B): T1 → T2
    Step 2 — precedence graph 
    T1 → T2  (from R1(A) before W2(A))
T2 → T1  (from R2(A) before W1(A))
→ Cycle: T1 → T2 → T1
    ResultThe precedence graph has a cycle. Therefore, the schedule is NOT conflict-serializable.
