    1. OOP concepts

    Object-oriented programming models the world as objects — bundles of state (fields) and behaviour (methods). Four pillars support it: encapsulation, abstraction, inheritance and polymorphism. The exam contrasts OOP with procedural programming.

    A class and an object — the foundation 
    class Animal {
    String name;     // state
    int age;

    void speak() {   // behaviour
        System.out.println(name + " makes a sound");
    }
}

// Creating an object
Animal a = new Animal();
a.name = "Tommy";
a.speak();   // Tommy makes a sound
    OOP vs procedural
    FeatureProcedural (C)OOP (Java)
    UnitFunctionObject (data + methods)
    Data accessGlobal or passed to functionsEncapsulated inside objects
    ReuseFunction librariesInheritance + composition
    ExtensibilityModify existing codeAdd subclasses without modifying
    ExampleC, Pascal, FortranJava, C++, Python, C#
    EncapsulationBundle data + methods; hide internals via private. Expose via getters/setters.
    AbstractionShow only essential features, hide implementation. Achieved via abstract classes and interfaces.
    InheritanceChild class reuses parent class code. extends for classes, implements for interfaces.
    Polymorphism"Many forms." Same method name, different behaviour. Compile-time (overloading) or runtime (overriding).

    2. Java platform — JDK, JRE, JVM

    Java's "write once, run anywhere" depends on compiling to bytecode (not native machine code) that runs on a virtual machine. The exam asks you to distinguish the three layers: JDK, JRE and JVM.

    Bytecode.java → javac → .class (bytecode). Bytecode is platform-independent; the JVM is platform-specific.
    JIT compilerJust-In-Time: the JVM compiles frequently-used bytecode to native code at runtime for speed.
    main signaturepublic static void main(String[] args) — public (JVM calls it), static (no object needed), void (returns nothing), String[] (command-line arguments).
    Primitive typesbyte(1), short(2), int(4), long(8), float(4), double(8), char(2), boolean. Everything else is a reference type (object on the heap).

    3. Access modifiers and keywords

    Java has four access levels that control who can see a class member. The exam asks for the visibility matrix and frequently tests static and final.

    Access modifier visibility
    ModifierSame classSame packageSubclass (other pkg)Everywhere
    privateYesNoNoNo
    (default)YesYesNoNo
    protectedYesYesYesNo
    publicYesYesYesYes
    static — belongs to the class, not the object 
    class Counter {
    static int count = 0;  // shared across all objects
    Counter() { count++; }
}

new Counter();
new Counter();
System.out.println(Counter.count);  // 2

    final methodCannot be overridden by a subclass.
    final classCannot be extended. String is final — you cannot subclass it.

    4. Constructors

    A constructor initialises a new object. It has the same name as the class and no return type. If you write no constructor, Java provides a default no-arg one.

    Default, parameterised and constructor chaining 
    class Animal {
    String name;
    int age;

    Animal() { this("Unknown", 0); }          // default → chains
    Animal(String name, int age) {            // parameterised
        this.name = name;
        this.age = age;
    }
}

Animal a1 = new Animal();               // Unknown, 0
Animal a2 = new Animal("Tommy", 3);     // Tommy, 3
    this()Calls another constructor in the same class. Must be the first statement.
    super()Calls the parent class constructor. Also must be first. If omitted, Java inserts super() (no-arg) implicitly.
    Constructor vs methodConstructor: no return type, same name as class, called once at creation. Method: has a return type, any name, called any number of times.

    5. Inheritance

    Inheritance lets a child class (Dog) reuse code from a parent class (Animal). The child gets all non-private fields and methods of the parent, plus it can add new ones or override existing ones.

    Single inheritance — Dog extends Animal 
    class Animal {
    String name;
    Animal(String name) { this.name = name; }
    void speak() { System.out.println(name + " makes a sound"); }
}

class Dog extends Animal {
    String breed;
    Dog(String name, String breed) {
        super(name);          // must call parent constructor
        this.breed = breed;
    }
    @Override
    void speak() { System.out.println(name + " barks"); }
}

Animal a = new Dog("Rex", "Labrador");
a.speak();  // Rex barks  (runtime polymorphism!)
    Rex barks
    Types of inheritance in Java
    TypeAllowed?How
    SingleYesclass B extends A
    MultilevelYesC extends B extends A
    HierarchicalYesB extends A, C extends A
    Multiple (classes)NoAmbiguity problem (diamond problem)
    Multiple (interfaces)Yesclass X implements I1, I2
    Why Java forbids multiple class inheritance. If class C extends both A and B, and both define display(), which one does C inherit? This is the diamond problem. Java avoids it by allowing multiple inheritance only through interfaces, where default methods have explicit conflict resolution.

    6. Polymorphism

    Polymorphism means "many forms." The same method call behaves differently depending on the context. The exam's repeat question is: compare overloading and overriding.

    Overloading (compile-time) — same name, different parameters 
    class MathUtil {
    int add(int a, int b)          { return a + b; }
    double add(double a, double b) { return a + b; }
    int add(int a, int b, int c)   { return a + b + c; }
}

MathUtil m = new MathUtil();
System.out.println(m.add(2, 3));       // 5 (int version)
System.out.println(m.add(2.5, 3.5));   // 6.0 (double version)
System.out.println(m.add(1, 2, 3));    // 6 (three-arg version)
    Overriding (runtime) — same signature, child redefines 
    class Animal {
    void speak() { System.out.println("Some sound"); }
}
class Dog extends Animal {
    @Override
    void speak() { System.out.println("Bark"); }
}

Animal a = new Dog();  // reference type: Animal, object type: Dog
a.speak();             // Bark — decided at RUNTIME
    Bark
    Overloading vs overriding — the repeat comparison
    FeatureOverloadingOverriding
    BindingCompile-time (static)Runtime (dynamic)
    ClassesSame classParent + child class
    Method nameSameSame
    ParametersMust differ (number, type or order)Must be identical
    Return typeCan differSame or covariant (subclass)
    AccessNo restrictionCannot be more restrictive
    static?Can overload static methodsCannot override static methods (hiding, not overriding)

    7. Abstract classes and interfaces

    Both abstract classes and interfaces define contracts — method signatures that implementing classes must fill in. The exam asks you to compare them and to know when to use which.

    Abstract class — partial implementation 
    abstract class Shape {
    String color;
    Shape(String color) { this.color = color; }
    abstract double area();     // no body — child must implement
    void display() {
        System.out.println(color + " shape, area=" + area());
    }
}

class Circle extends Shape {
    double r;
    Circle(String color, double r) { super(color); this.r = r; }
    @Override
    double area() { return Math.PI * r * r; }
}

new Circle("Red", 5).display();  // Red shape, area=78.539...
    Interface — pure contract (pre-Java 8) 
    interface Drawable {
    void draw();   // implicitly public abstract
}

class Circle extends Shape implements Drawable {
    // ... must implement both area() AND draw()
    @Override
    public void draw() { System.out.println("Drawing circle"); }
}
    Abstract class vs interface
    FeatureAbstract classInterface
    MethodsAbstract + concreteAbstract (+ default/static since Java 8)
    FieldsAny (instance + static)Only public static final constants
    ConstructorYesNo
    MultipleCan extend only oneCan implement many
    AccessAny modifierImplicitly public
    When to useIS-A with shared codeCAN-DO capability

    8. Exception handling

    An exception is an event that disrupts normal program flow. Java forces you to handle checked exceptions at compile time, while unchecked exceptions (runtime errors like NullPointerException) are optional to catch. The exam tests both the mechanism and the throw vs throws distinction.

    try-catch-finally — the core mechanism 
    try {
    int result = 10 / 0;          // throws ArithmeticException
    System.out.println(result);   // never reached
} catch (ArithmeticException e) {
    System.out.println("Error: " + e.getMessage());
} finally {
    System.out.println("Always runs");
}
    Error: / by zero Always runs
    throw vs throws
    Featurethrowthrows
    PurposeActually throw an exceptionDeclare that a method may throw
    LocationInside method bodyIn method signature
    CountOne exception at a timeMultiple: throws A, B
    Examplethrow new IOException("fail")void read() throws IOException
    finallyAlways executes — even after a return inside try or catch. Used for cleanup (closing files, connections).
    try-with-resourcestry (BufferedReader br = new BufferedReader(...)) — auto-closes the resource. The class must implement AutoCloseable.

    9. Strings

    Java String objects are immutable — once created, their content cannot change. Every operation that appears to modify a string actually creates a new object. This is the key to understanding == vs .equals() and the string pool.

    Immutability and the string pool 
    String s1 = "Hello";       // goes to string pool
String s2 = "Hello";       // reuses same pool object
String s3 = new String("Hello");  // new object on heap

System.out.println(s1 == s2);       // true  (same pool ref)
System.out.println(s1 == s3);       // false (different objects)
System.out.println(s1.equals(s3));  // true  (same content)
    true false true
    String vs StringBuffer vs StringBuilder
    FeatureStringStringBufferStringBuilder
    MutabilityImmutableMutableMutable
    Thread-safeYes (immutable)Yes (synchronized)No
    PerformanceSlow for concatenationSlower than SBFastest
    Use caseFew modificationsMulti-threaded + modificationSingle-threaded + modification
    Why immutability matters for the exam. s1.concat(" World") does NOT change s1 — it returns a new String. If you don't assign the result, the concatenation is lost: s1.concat("!"); System.out.println(s1); still prints "Hello".

    10. Collections framework

    The Collections framework is Java's standard library for dynamic data structures. It replaces arrays when you need resizing, ordering, uniqueness or key-value mapping. The exam asks for hierarchy knowledge and comparison tables.

    ArrayList vs LinkedList — the standard comparison
    FeatureArrayListLinkedList
    Backed byDynamic arrayDoubly linked list
    Get by indexO(1)O(n)
    Add/remove at endsO(1) amortised / O(n)O(1)
    MemoryLess (contiguous)More (node pointers)
    HashMapKey→value. Allows one null key. O(1) average get/put. Not thread-safe.
    HashtableLike HashMap but synchronized (thread-safe) and no null keys/values. Legacy class.
    ConcurrentHashMapThread-safe without locking the entire map (segment-level locking). Preferred over Hashtable.

    11. Multithreading

    A thread is the smallest unit of execution. Java supports multithreading natively — you can create threads by extending Thread or implementing Runnable. The exam focuses on the lifecycle and on sleep vs wait.

    Two ways to create a thread 
    // Way 1: extend Thread
class MyThread extends Thread {
    public void run() { System.out.println("Thread running"); }
}
new MyThread().start();

// Way 2: implement Runnable (preferred — allows extending another class)
class MyTask implements Runnable {
    public void run() { System.out.println("Task running"); }
}
new Thread(new MyTask()).start();
    sleep() vs wait()
    Featuresleep()wait()
    ClassThreadObject
    LockDoes NOT releaseReleases the lock
    Wake-upAfter timeoutBy notify()/notifyAll()
    Called fromAnywhereInside synchronized block
    PurposePause for a durationInter-thread communication

    13. Output prediction patterns

    Java output questions test the same small set of traps. Knowing the traps means you can trace mechanically instead of guessing.

    Trap 1: String == vs equals 
    String a = "Java";
String b = "Java";
String c = new String("Java");
System.out.println(a == b);       // true  (same pool object)
System.out.println(a == c);       // false (different objects)
System.out.println(a.equals(c));  // true  (same content)
    true false true
    Trap 2: finally always runs 
    static int test() {
    try { return 1; }
    finally { return 2; }    // overrides the try's return!
}
System.out.println(test());  // 2
    2
    Trap 3: method overriding with parent reference 
    class A {
    void show() { System.out.println("A"); }
}
class B extends A {
    void show() { System.out.println("B"); }
}

A obj = new B();    // reference: A, object: B
obj.show();         // B — runtime polymorphism
    B
    Full trap catalogue for Java output questions
    TrapRule to apply
    == on stringsCompares references, not content. Use .equals().
    finally returnfinally's return overrides try/catch returns.
    Dynamic dispatchMethod is chosen by the actual object type, not the reference type.
    Static bindingOverloaded methods are resolved at compile time based on reference type.
    String immutabilitys.concat("x") returns new String; s is unchanged if not reassigned.

    P2 Why does Java not support multiple inheritance through classes? How do interfaces solve the problem?
    The diamond problem 
    // Hypothetical — Java does NOT allow this
class A { void show() { ... } }
class B extends A { void show() { ... } }
class C extends A { void show() { ... } }
class D extends B, C { }  // WHICH show() does D inherit?

    The ambiguity is the diamond problem: D inherits two conflicting show() implementations.

    Interfaces solve it — explicit conflict resolution 
    interface I1 { default void show() { System.out.println("I1"); } }
interface I2 { default void show() { System.out.println("I2"); } }

class D implements I1, I2 {
    // Compiler forces you to resolve the conflict:
    @Override
    public void show() {
        I1.super.show();  // explicitly choose I1's version
    }
}

    P8 What is the difference between == and .equals() in Java?
    OperatorComparesFor primitivesFor objects
    ==Memory addressValues (works correctly)References (same object?)
    .equals()ContentN/A (primitives can't call methods)Content (if overridden)
     
    Integer a = 128;
Integer b = 128;
System.out.println(a == b);       // false (outside cache range -128 to 127)
System.out.println(a.equals(b));  // true  (same value)

Integer c = 127;
Integer d = 127;
System.out.println(c == d);       // true  (cached by JVM: -128 to 127)
    The Integer cache trap. Java caches Integer objects for values −128 to 127. Within this range, == returns true because both references point to the same cached object. Outside this range, new objects are created, so == returns false.
