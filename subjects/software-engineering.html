    1. Process models

    A software process model prescribes the order of phases from requirements through delivery. The exam compares models and asks which fits a given project scenario.

    ModelFlowBest forKey weakness
    WaterfallLinear, sequentialStable, well-understood requirementsNo backtracking; late testing
    V-ModelWaterfall + parallel test planningSafety-critical systemsStill rigid; requirements must be stable
    IterativeRepeated refinement cyclesEvolving requirementsScope creep without discipline
    SpiralRisk-driven, prototyping cyclesHigh-risk, large projectsComplex to manage; needs risk expertise
    Agile (Scrum)Short sprints (2–4 weeks), daily standupsFast delivery, changing requirementsNeeds engaged customer; less documentation
    RADPrototyping + component reuseSmall-to-medium, tight deadlinesNeeds modular design; doesn't scale
    IncrementalDeliver in increments, each adding featuresGetting a core product out quicklyNeeds good architectural planning upfront

    Agile manifesto values (memorise for essay questions):

    • Individuals and interactions over processes and tools
    • Working software over comprehensive documentation
    • Customer collaboration over contract negotiation
    • Responding to change over following a plan
    The Spiral model is unique in being risk-driven — each iteration starts with risk analysis. If risk is low, the spiral may resemble waterfall; if high, it may produce more prototypes before committing to design.

    2. Requirements engineering

    Functional requirements describe what the system does (features, behaviours). Non-functional requirements describe how well it does it (performance, security, usability, reliability).

    NFR categoryMeasurable metricExample
    PerformanceResponse time, throughput< 2s page load under 1000 concurrent users
    ReliabilityMTBF, uptime %99.9% availability (8.76 hrs downtime/year)
    SecurityEncryption standard, audit complianceAll data encrypted with AES-256
    UsabilityTask completion rate, learnabilityNew user completes core task in < 5 min
    ScalabilityLoad capacitySupport 10× current users without re-architecture

    Requirements engineering process:

    1. Elicitation

      Gather requirements via interviews, questionnaires, observation, document analysis, prototyping.

    2. Analysis

      Resolve conflicts, prioritise (MoSCoW: Must/Should/Could/Won't).

    3. Specification

      Write the SRS (Software Requirements Specification) document.

    4. Validation

      Reviews, prototyping, test-case generation to confirm requirements are correct, complete and consistent.

    The cost of fixing a requirements error grows exponentially with project phase — 100× more expensive in maintenance than in requirements. This is why requirements engineering gets so much exam attention.

    3. Analysis and design

    Coupling measures inter-module dependency (low is better). Cohesion measures intra-module relatedness (high is better).

    Coupling (worst → best)Cohesion (worst → best)
    Content → Common → External → Control → Stamp → Data Coincidental → Logical → Temporal → Procedural → Communicational → Sequential → Functional

    Architecture styles: layered (UI → business → data), client-server, pipe-and-filter, event-driven, microservices, MVC (Model-View-Controller).

    SOLID principles (object-oriented design):

    • Single Responsibility — one class, one reason to change
    • Open/Closed — open for extension, closed for modification
    • Liskov Substitution — subtypes must be substitutable for their base
    • Interface Segregation — no client should depend on unused methods
    • Dependency Inversion — depend on abstractions, not concretions
    "Low coupling, high cohesion" is the single most-repeated principle in SE exams. If a question asks about "good design", this is usually the answer they want.

    4. UML diagrams

    UML (Unified Modeling Language) has 14 diagram types, but the exam focuses on about 5. Here are the key structural and behavioural diagrams:

    DiagramTypeShowsKey elements
    Use caseBehaviouralActor–system interactionsActors, use cases, include/extend
    ClassStructuralClasses, attributes, methods, relationshipsAssociation, aggregation, composition, inheritance
    SequenceBehaviouralObject interactions over timeLifelines, messages, activation bars
    ActivityBehaviouralWorkflow / process flowActions, decisions, fork/join, swimlanes
    StateBehaviouralObject lifecycle statesStates, transitions, events, guards

    Class diagram relationships:

    • Association (solid line): general "uses" relationship
    • Aggregation (hollow diamond): "has-a", part can exist independently
    • Composition (filled diamond): "owns-a", part destroyed with whole
    • Inheritance (hollow triangle arrow): "is-a", generalization
    • Dependency (dashed arrow): temporary "uses"
    «include» means the base use case always invokes the included one (mandatory). «extend» means it sometimes adds extra behaviour (optional, at extension points). A common exam question asks you to distinguish these.

    5. Design patterns

    The Gang of Four (GoF) catalogued 23 design patterns in three categories. The exam typically asks for pattern identification from a scenario.

    CategoryPatternPurpose
    CreationalSingletonExactly one instance (e.g. DB connection pool)
    Factory MethodSubclass decides which class to instantiate
    Abstract FactoryFamily of related objects without specifying concrete classes
    StructuralAdapterConvert one interface to another (wrapper)
    DecoratorAdd responsibilities dynamically
    FacadeSimplified interface to a complex subsystem
    BehaviouralObserverOne-to-many notification (pub-sub)
    StrategyFamily of interchangeable algorithms
    IteratorSequential access without exposing internal structure
    Singleton pattern (Java) -- ensures one instance 
    public class ConfigManager {
    private static ConfigManager instance = null;

    private ConfigManager() { }  // private constructor

    public static ConfigManager getInstance() {
        if (instance == null) {
            instance = new ConfigManager();
        }
        return instance;
    }

    public String getSetting(String key) { /* ... */ }
}

// Usage: ConfigManager.getInstance().getSetting("db.host");
    Singleton, Observer and Factory are the three patterns most asked about. Know the structure and a real-world example for each. Singleton: logger, config manager. Observer: event listeners, MVC. Factory: UI toolkit creating platform-specific widgets.

    6. Software testing

    Testing levels (from smallest to largest scope):

    LevelTestsWho
    UnitIndividual functions/methodsDeveloper
    IntegrationModule interfaces and interactionsDeveloper/Tester
    SystemComplete system against requirementsQA team
    AcceptanceUser validates real-world scenariosCustomer/User

    White-box (structural) testing: tests based on internal code structure. Techniques: statement coverage, branch coverage, path coverage, condition coverage.

    Black-box (functional) testing: tests based on requirements without knowledge of internals. Techniques: equivalence partitioning, boundary value analysis, decision table testing.

    Boundary value analysis example: for an input field accepting ages 18–65, test values: 17, 18, 19, 64, 65, 66.

    Other testing types:

    • Regression: re-running tests after changes to ensure nothing broke
    • Smoke: quick surface-level check that build is stable
    • Alpha: in-house testing by developers/testers
    • Beta: testing by a limited group of real users
    Cyclomatic complexity = E − N + 2P
    E = edges, N = nodes, P = connected components in the control flow graph
    Gives the minimum number of independent paths to test
    The V-model maps each development phase to a testing level: requirements ↔ acceptance, design ↔ system, detailed design ↔ integration, coding ↔ unit. This pairing is a frequent exam question.

    7. Estimation techniques

    COCOMO (Constructive Cost Model) — Boehm's model for estimating effort from lines of code (KLOC):

    ModeEffort (PM)Time (months)Project type
    Organic2.4 × (KLOC)1.052.5 × (Effort)0.38Small team, familiar domain
    Semi-detached3.0 × (KLOC)1.122.5 × (Effort)0.35Medium complexity
    Embedded3.6 × (KLOC)1.202.5 × (Effort)0.32Complex, tightly constrained

    Example: Estimate effort for a 32 KLOC organic project.

    Effort = 2.4 × (32)1.05
    321.05 ≈ 32 × 320.05 ≈ 32 × 1.189 ≈ 38.05
    Effort ≈ 2.4 × 38.05 ≈ 91.3 person-months
    Time = 2.5 × (91.3)0.38 ≈ 2.5 × 6.52 ≈ 16.3 months
    Staff = 91.3/16.3 ≈ 6 people

    Function Point Analysis (FPA) — estimates size based on functionality rather than code:

    Function typeLowAverageHigh
    External Inputs (EI)346
    External Outputs (EO)457
    External Inquiries (EQ)346
    Internal Logical Files (ILF)71015
    External Interface Files (EIF)5710
    UFP = Σ(count × weight) for each function type
    FP = UFP × [0.65 + 0.01 × Σ(Fi)]
    Fi = 14 general system characteristics, each rated 0–5
    COCOMO uses lines of code (after-the-fact measure), while Function Points use functionality (before coding). FP is language-independent, making it better for early estimation.

    8. Project management

    CPM/PERT — scheduling techniques based on activity networks:

    • CPM (Critical Path Method): deterministic durations. The critical path is the longest path through the network — it determines project duration. Activities on it have zero slack.
    • PERT: probabilistic durations using three estimates: te = (to + 4tm + tp)/6

    Example CPM calculation:

    ActivityDurationDepends onESEFLSLFSlack
    A3—03030
    B4A37370
    C2A35572
    D5B,C7127120
    Critical path: A → B → D (duration = 3+4+5 = 12)
    Activity C has 2 days of slack — can be delayed without affecting project end

    Gantt chart: bar chart showing activities on a timeline. Good for visualisation but doesn't show dependencies. PERT/CPM network diagrams show dependencies but are harder to read.

    The critical path is critical because any delay on it delays the whole project. Project managers focus resources on critical-path activities. Slack on non-critical activities shows how much schedule flexibility exists.

    9. Maintenance and quality

    Software maintenance consumes 60–80% of total lifecycle cost. Four types:

    TypePurpose% of effort
    CorrectiveFix bugs discovered after release~20%
    AdaptiveAdapt to changes in environment (OS, hardware, regulations)~25%
    PerfectiveImprove performance, add features requested by users~50%
    PreventiveRefactor to prevent future problems~5%

    Software quality metrics:

    • Defect density: defects per KLOC
    • MTBF: mean time between failures
    • Reliability: R(t) = e−λt where λ = 1/MTBF

    CMM/CMMI levels (Capability Maturity Model):

    LevelNameCharacteristic
    1InitialAd hoc, unpredictable
    2ManagedBasic project management
    3DefinedStandard processes across organisation
    4Quantitatively ManagedMetrics-driven process control
    5OptimizingContinuous process improvement
    Total lifecycle cost of a 50 KLOC banking system: ~100 person-months development
    Maintenance = 60–80% of lifecycle ≈ 0.7 × total ≈ 70% of cost
    Corrective (bugs): 20% × 70 = 14 person-months
    Adaptive (environment): 25% × 70 = 17.5 person-months
    Perfective (features): 50% × 70 = 35 person-months
    Preventive (refactor): 5% × 70 = 3.5 person-months
    Perfective dominates -- most maintenance effort goes to new features, not fixing bugs
    Perfective maintenance (adding features, improving performance) accounts for roughly half of maintenance effort — not bug fixing as most people assume. This is a common exam trick question.

    S2 Differentiate between functional and non-functional requirements with examples for a banking application. standard repeat

    Functional requirements (what the system does):

    • User shall be able to transfer funds between accounts
    • System shall generate monthly account statements
    • System shall validate OTP before completing transactions

    Non-functional requirements (how well it performs):

    • Performance: Transaction response time < 3 seconds
    • Security: All data encrypted in transit and at rest (AES-256)
    • Availability: 99.99% uptime (52.6 min downtime/year)
    • Scalability: Support 10,000 concurrent users
    • Usability: Comply with WCAG 2.1 AA accessibility
    S3 Draw a use-case diagram for an online library management system. standard repeat

    Actors: Member, Librarian, System (timer)

    Use cases:

    • Member: Search Book, Borrow Book, Return Book, View Account
    • Librarian: Add Book, Remove Book, Manage Members, Generate Reports
    • System: Send Overdue Notice (extends Borrow Book at extension point "overdue check")

    Relationships:

    • Borrow Book «include» Verify Membership (always verified)
    • Borrow Book «extend» Send Overdue Notice (only if overdue)
    • Librarian inherits all Member use cases (generalisation)

    • White-box: ensure all branches in the authentication code are covered — the password hash comparison, the account-locked check, the 2FA path
    S6 Explain coupling and cohesion. Why is "low coupling, high cohesion" desirable? standard repeat

    Coupling = degree of interdependence between modules. High coupling means a change in one module forces changes in others → fragile, hard to maintain.

    Cohesion = degree to which elements within a module belong together. High cohesion means a module does one thing well → easier to understand, test, reuse.

    Why desirable:

    • Changes are localised — modifying one module doesn't cascade
    • Modules can be tested independently
    • Modules can be reused in other projects
    • Teams can work on different modules in parallel

    Example: A module that handles both PDF generation and email sending has low cohesion. Split into PDFGenerator and EmailSender → high cohesion, and they communicate through a defined interface → low coupling.

    S7 What is the Spiral model? What makes it different from other models? standard repeat

    The Spiral model (Boehm, 1988) combines iterative development with systematic risk management. Each cycle through the spiral has four quadrants:

    1. Planning

      Determine objectives, alternatives, constraints.

    2. Risk analysis

      Identify and evaluate risks; build prototypes to mitigate.

    3. Engineering

      Develop and verify the product.

    4. Evaluation

      Customer reviews; plan next iteration.

    Unique features:

    • Risk-driven — each iteration starts with risk analysis
    • Subsumes other models — low-risk spiral ≈ waterfall; high-risk ≈ prototyping
    • Best for large, complex, high-risk projects
    S8 Find the critical path: A(3)→, B(4)→D(5), C(2)→D(5), A→B, A→C. standard repeat

    Network: A→B→D, A→C→D

    Path 1: A→B→D = 3+4+5 = 12
    Path 2: A→C→D = 3+2+5 = 10
    Critical path = A→B→D = 12 days
    Activity C has slack = 12−10 = 2 days
    S9 Describe the four types of software maintenance with examples. standard repeat
    TypePurposeExample
    CorrectiveFix defectsFixing a calculation error in interest computation
    AdaptiveAdapt to environment changesMigrating from Windows Server 2016 to 2022
    PerfectiveImprove functionality/performanceAdding multi-currency support to a banking app
    PreventivePrevent future problemsRefactoring spaghetti code to reduce technical debt

    S10 Calculate cyclomatic complexity for a function with 12 edges, 9 nodes and 1 connected component in its control flow graph. standard repeat
    V(G) = E − N + 2P = 12 − 9 + 2(1) = 5

    This means there are 5 independent paths through the code, and you need at least 5 test cases for complete path coverage.

    McCabe's guideline: cyclomatic complexity > 10 suggests the function is too complex and should be refactored.

    P1 A system has 5 external inputs (avg), 3 external outputs (avg), 2 inquiries (low), 4 ILFs (avg) and 1 EIF (low). Calculate the unadjusted function points. practice
    EI: 5 × 4 = 20
    EO: 3 × 5 = 15
    EQ: 2 × 3 = 6
    ILF: 4 × 10 = 40
    EIF: 1 × 5 = 5
    UFP = 20+15+6+40+5 = 86 function points
    P2 What are the SOLID principles? Give an example of violating the Single Responsibility Principle. practice
    • S — Single Responsibility: a class should have only one reason to change
    • O — Open/Closed: open for extension, closed for modification
    • L — Liskov Substitution: subtypes must be usable wherever their base type is expected
    • I — Interface Segregation: prefer many small interfaces to one large one
    • D — Dependency Inversion: high-level modules should not depend on low-level modules; both should depend on abstractions

    SRP violation example: A UserService class that handles user registration, sends welcome emails, generates reports and manages authentication. It has four reasons to change. Fix: split into UserRegistration, EmailService, ReportGenerator and AuthService.

    P3 A project has activities: A(2), B(3, depends A), C(4, depends A), D(2, depends B), E(3, depends C,D). Find the critical path and project duration. practice

    Paths through the network:

    A→B→D→E = 2+3+2+3 = 10
    A→C→E = 2+4+3 = 9
    Critical path = A→B→D→E = 10 days

    Note: E depends on both C and D, so E cannot start until both are finished. On the critical path, D finishes at day 7, C finishes at day 6, so E starts at day 7.

    P4 Explain the Singleton design pattern. Write the pseudocode. practice

    Intent: ensure a class has exactly one instance and provide a global point of access.

    Structure:

    class Singleton {
    private static instance = null;

    private Singleton() { }  // private constructor

    public static getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}

    Use cases: database connection pool, logger, configuration manager, thread pool.

    Thread-safety note: the lazy initialisation above is not thread-safe. Use synchronized/double-checked locking or eager initialisation for concurrent access.

    P9 What is regression testing? Why is it important in agile? practice

    Regression testing re-executes previously passed test cases after code changes to ensure new modifications haven't broken existing functionality.

    Importance in agile:

    • Frequent sprints mean frequent code changes → higher risk of regression
    • Automated regression suites (CI/CD) catch regressions within minutes
    • Without regression testing, each sprint could unknowingly break features from previous sprints
    • Enables confident refactoring — developers can restructure code knowing tests will catch breakages

    Types: full regression (re-run everything), selective regression (re-run tests related to changed modules), priority-based (re-run high-priority tests first).

    P10 Use PERT to estimate duration for an activity with optimistic=5, most likely=8, pessimistic=17 days. Also calculate the standard deviation. practice
    te = (to + 4tm + tp)/6 = (5 + 4×8 + 17)/6
    = (5 + 32 + 17)/6 = 54/6 = 9 days
    σ = (tp − to)/6 = (17 − 5)/6 = 12/6 = 2 days
    Variance = σ² = 4
    95% confident the duration is within te ± 2σ = 9 ± 4 = 5 to 13 days
