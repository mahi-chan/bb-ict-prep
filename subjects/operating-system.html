    1. Fundamentals

    An operating system sits between the hardware and the user's programs and plays two roles at once. As a resource manager it allocates CPU, memory, storage and devices among competing processes. As an extended (virtual) machine it hides hardware detail behind clean abstractions — files instead of disk sectors, processes instead of registers, sockets instead of interrupt lines.

    Both roles need the same thing underneath: the OS must be able to do things that user programs cannot. Follow one ordinary line of C and you can see exactly where that boundary sits and how it is crossed.

    What actually happens when a program prints "Hello"
    C — three lines, one trip into the kernel
    #include <stdio.h>
int main(void) {
    printf("Hello\n");     /* looks like an ordinary function call */
    return 0;
}
    Hello

    printf is not a system call. It is an ordinary library function running in user mode: it formats the string into a buffer, and then has to ask the kernel to do the one thing it cannot do itself — touch the terminal device. That request is the system call write(1, "Hello\n", 6), and this is the journey:

    1. Still in user mode

      printf formats the text and calls the C library's write wrapper. Everything so far is ordinary code — the CPU would run it for any program, privileged or not.

    2. The wrapper prepares the request

      It loads the system-call number for write into a register (1 on x86-64 Linux) and the three arguments into others, then executes the trap instruction — syscall on x86-64, int 0x80 on older systems.

    3. The boundary is crossed

      The trap is the only way up. In a single hardware step it flips the mode bit to kernel mode and jumps to a fixed kernel entry point — an address the user program never chose and cannot change. The two happen together, which is the whole trick.

    4. Now in kernel mode

      The kernel looks the number up in the system-call table, validates the arguments — is descriptor 1 really open? does the buffer lie inside this process's own memory? — and calls the terminal driver.

    5. And back down

      The driver writes the bytes. The kernel places the return value (6, the byte count) in a register, flips the mode bit back to user, and resumes the program at the instruction after the trap. The program never knew it left.

    That one bit is the whole of OS protection. A user program cannot simply set the mode bit itself, because the instruction that changes it is itself privileged. Its only route into kernel mode is a trap, and a trap always arrives at an address the kernel chose in advance. So a program cannot write directly to disk, disable interrupts, or read another process's memory — not because the compiler refuses, but because the CPU refuses, and the single door is one the OS is standing behind. Every protection guarantee in the rest of this subject — memory isolation, file permissions, scheduling fairness — is ultimately this bit plus the MMU.

    2. Types of operating system

    The names below are usually memorised as a list, which makes them easy to confuse. They are better understood as one idea developed in stages: each type exists because the previous one wasted something. Watch three jobs run and the progression explains itself.

    Three identical jobs, two different systems

    Each job needs 2 units of CPU, then waits 6 units for I/O (a disk read, say), then needs 2 more units of CPU. So each job needs 4 units of CPU and takes at least 10 units of wall-clock time.

    FormulaCPU utilisation = CPU busy time / total elapsed time
    Uniprogramming3 jobs × 4 units CPU = 12 busy, finishes at 30 utilisation = 12 / 30 = 40%
    Multiprogrammingsame 12 units busy, finishes at 14 utilisation = 12 / 14 = 85.7%
    Resultthe same work, done in 14 units instead of 30 — a 2.1× throughput gain from no extra hardware
    Multiprogramming buys throughput with memory, not speed. No job ran faster — J1 still finished at time 10 in both timelines. What changed is that the idle stretches got filled, and the only thing that made that possible was holding all three jobs in memory at once so the CPU had somewhere to go. This is why memory management and scheduling arrive together in the syllabus: you cannot have one without the other. It is also why the residual 2-unit gap at t = 6–8 exists — at that instant every job in memory was blocked, and the cure is to raise the degree of multiprogramming by admitting a fourth job.
    And where time-sharing differs

    Multiprogramming switches only when the running job blocks. Add a fourth job that never does any I/O — a 20-unit calculation — and it takes the CPU at t = 0 and holds it until t = 20, while J1, J2 and J3 sit ready and untouched. Nothing in multiprogramming can take it away.

    Time-sharing fixes exactly this by adding a timer interrupt: after a fixed quantum the hardware forces a trap into the kernel whether the job likes it or not, and the scheduler picks someone else. That single addition is the whole difference — multiprogramming optimises for CPU utilisation, time-sharing gives up a little of it in exchange for response time, which is what makes an interactive terminal usable.

    3. Processes and threads

    Program
    A passive entity — an executable file sitting on disk.
    Process
    A program in execution — an active entity with a program counter, stack, data section, heap and a set of resources. One program can spawn many processes.

    Process Control Block (PCB) — the kernel's record of a process, and what a context switch saves and restores. Contents: process ID, process state, program counter, CPU registers, CPU scheduling information (priority, queue pointers), memory-management information (base and limit registers, page or segment tables), accounting information (CPU used, time limits), and I/O status (open files, allocated devices).

    Context switch — save the current process's state into its PCB, load the next process's state from its PCB. It is pure overhead: no useful work happens during it, typically a few microseconds, and it also costs indirectly by flushing the TLB and polluting the cache.

    Process creation system calls (Unix)

    Zombie and orphan

    A zombie has finished executing, but its parent has not yet called wait(), so its PCB entry lingers to hold the exit status. It consumes no CPU or memory, only a process-table slot — but a parent that never reaps can exhaust the table. An orphan is still running when its parent dies; it is immediately re-parented to init/systemd (PID 1), which reaps it properly. Zombie = dead child, live parent. Orphan = live child, dead parent.

    Threading models. Many-to-one: many user threads mapped to one kernel thread — cheap, but one blocking call stops everything and no true parallelism. One-to-one: each user thread has its own kernel thread — real parallelism, but thread creation costs a kernel object (Linux, Windows). Many-to-many: m user threads multiplexed onto n ≤ m kernel threads — the flexible compromise.

    Benefits of multithreading: responsiveness (the UI thread stays alive while a worker computes), resource sharing (no IPC setup needed), economy (creation and switching are far cheaper than for processes), and scalability (threads run genuinely in parallel on a multicore CPU, whereas a single-threaded process cannot).

    4. CPU scheduling

    Several processes are ready; one CPU. The short-term scheduler decides who runs next, and that single decision rule is the whole subject. Exam questions almost never ask you to define an algorithm — they give you arrival times and burst times and ask you to run it and compute the averages. So the only way to learn this is to watch one set of processes go through every algorithm.

    The four quantities — get these definitions exactly right Completion time (CT) = the instant the process finishes Turnaround time (TAT) = CT − Arrival time (total time in the system) Waiting time (WT) = TAT − Burst time (time spent in the ready queue) Response time (RT) = first time on CPU − Arrival time Average WT = ΣWT / n Average TAT = ΣTAT / n Throughput = processes completed per unit time CPU utilisation = busy time / total time

    The one worth pausing on is waiting time. It is not "time before it starts" — a preempted process keeps accumulating waiting time every time it is pushed back into the ready queue. Deriving it as TAT − BT rather than reading it off the chart is what stops this going wrong.

    Choosing the round-robin quantum

    Too large and round robin degenerates into FCFS, losing its response-time advantage. Too small and context-switch overhead dominates — with a 1 ms quantum and a 0.1 ms switch, 9% of the CPU is wasted. The rule of thumb is that about 80% of CPU bursts should be shorter than one quantum, which in practice means 10–100 ms.

    5. Process synchronisation

    A race condition occurs when the result depends on the order in which concurrent processes touch shared data. The description sounds abstract until you see where the gap actually is — so here is the smallest possible example, in full.

    How one increment loses money

    Two threads each run balance++ on a shared account holding 500. One line of C. But the CPU has no "increment memory" step — it must load, add, and store back:

    What balance++ compiles to
    load   R1, balance      ; copy the value from memory into a register
add    R1, 1            ; increment the register
store  balance, R1      ; write the register back to memory

    Each thread has its own registers, but they share the one balance in memory. A context switch can land between any two of those instructions. Here is the interleaving that loses an update:

    StepThreadInstructionT1's R1T2's R1balance in memory
    1T1load R1, balance500—500
    2T1add R1, 1501—500
    context switch — T1 is preempted before it can store
    3T2load R1, balance501500500
    4T2add R1, 1501501500
    5T2store balance, R1501501501
    context switch back to T1, which resumes at its store
    6T1store balance, R1501501501
    Expected500 + 1 + 1 = 502
    Actual501 — one deposit has vanished, and no instruction failed

    The damage is done at step 3. T2 read 500, a value that was already stale — T1 had computed 501 but had not yet written it. T2's store at step 5 was then overwritten by T1's at step 6. Both threads did exactly what they were told; the arithmetic is correct in both registers. The bug is entirely in the interleaving.

    This is why race conditions are so dangerous in practice. Run those two threads a million times and the interleaving above may occur once — the switch has to land in exactly that two-instruction window. The program passes every test, works in staging, and corrupts an account under production load. It is also why "just add a print statement" makes the bug disappear: printing changes the timing. The only reliable answer is not better luck but a structural guarantee that steps 1–3 cannot be interleaved at all — which is what the critical-section problem asks for.
    The critical-section problem — three requirements
    1. Mutual exclusion — at most one process inside the critical section at a time.
    2. Progress — if no process is in the critical section, the choice of who enters next cannot be postponed indefinitely, and only processes wanting to enter may take part in that decision.
    3. Bounded waiting — there is a limit on how many times other processes may enter after a process has requested entry and before it is granted.
    Peterson's solution — mutual exclusion with no special hardware

    Two processes, two shared variables, and nothing but ordinary loads and stores. It is worth reading closely because it shows that the problem is solvable in software at all.

    C — Peterson's algorithm for processes 0 and 1
    bool flag[2] = { false, false };   /* flag[i] = "I want to enter"  */
int  turn;                         /* whose go it is if both want it */

/* process i, where j = 1 - i is the other one */
void process(int i) {
    int j = 1 - i;
    while (true) {
        flag[i] = true;                    /* 1. announce my intent   */
        turn    = j;                       /* 2. politely defer to j  */
        while (flag[j] && turn == j)
            ;                              /* 3. busy-wait            */

        /* ---- critical section ---- */

        flag[i] = false;                   /* 4. release              */

        /* ---- remainder section ---- */
    }
}

    Line 2 is the one that looks wrong and is the one that makes it work. Each process sets turn to the other process, giving away its own turn. If both arrive at once, both write turn — and whichever write lands second wins, because it is the last value stored. So exactly one process finds turn pointing away from itself and proceeds.

    Both processes arrive simultaneously — P0's write to turn lands first

    Check it against all three requirements. Mutual exclusion — entry needs flag[j] false or turn ≠ j, and since turn holds one value, both cannot be true at once. Progress — if P1 does not want in, flag[1] is false and P0 never blocks. Bounded waiting — after P0 leaves it must set turn = 1 before re-entering, so P1 waits at most one turn.

    Peterson's algorithm does not work on a real modern CPU. The correctness argument above assumes step 3 happens after step 1 in the order written. An out-of-order processor is free to reorder independent loads and stores, and flag[i] = true and turn = j touch different addresses — so the hardware may commit them in the other order, and both processes can enter. The fix is a memory barrier between them. This is exactly why real systems use hardware atomics such as compare-and-swap rather than clever software: the atomicity has to come from the hardware in the end.

    Hardware support. TestAndSet(lock) atomically returns the old value and sets the lock to true; Swap(a, b) atomically exchanges two words; compare-and-swap generalises both. These give mutual exclusion trivially, but a naive spin loop violates bounded waiting unless a waiting array is added.

    empty and full are counting semaphores doing the accounting — they always sum to N, and blocking on them is how a producer waits for space or a consumer waits for data. mutex is binary and does something else entirely: it stops two producers writing to the same slot.

    Swap the producer's two waits and you get a deadlock. Write wait(mutex) before wait(empty) and consider a full buffer: the producer takes the mutex, then blocks on empty — while still holding the mutex. The consumer now wants the mutex to remove an item and free a slot, but the producer is holding it and will not let go until a slot is freed. Each waits for the other, permanently. The rule this illustrates is general: never block on a counting semaphore while holding a lock. Acquire the resource count first, the mutex second, and release in the opposite order.

    Priority inversion — a high-priority task blocks on a lock held by a low-priority task, which is itself preempted by a medium-priority task, so the high-priority task waits behind the medium one. The Mars Pathfinder rover suffered exactly this in 1997. Cure: priority inheritance, where the lock holder temporarily inherits the highest priority of anyone waiting on it.

    6. Deadlock

    The four Coffman conditions — all four must hold simultaneously
    1. Mutual exclusion — at least one resource is non-shareable.
    2. Hold and wait — a process holding a resource is waiting for another.
    3. No preemption — a resource can only be released voluntarily by the process holding it.
    4. Circular wait — a closed chain of processes exists, each waiting for a resource held by the next.
    Can a single process deadlock itself?

    Yes. Circular wait requires a cycle, but a cycle of length one is still a cycle: a process holding resource R and then requesting R again — a non-recursive mutex locked twice by the same thread — waits forever for itself. All four Coffman conditions hold. In practice this is why recursive mutexes exist. Worked in full at solved question 2.

    Seeing it — the resource allocation graph

    Processes are circles, resources are rectangles with one dot per instance. A request edge runs process → resource ("I want this"); an assignment edge runs resource → process ("this is yours"). Draw two processes each holding what the other needs:

    A cycle proves deadlock only when every resource is single-instance. Give R1 a second dot — two identical printers, say — and the same picture is no longer fatal: P2's request for R1 can be satisfied by the free second instance, P2 then completes, releases R2, and P1 proceeds. The cycle is still drawn on the page but nobody is stuck. So with multiple instances a cycle is necessary but not sufficient, and the graph stops being a decision procedure. That is precisely the gap the banker's algorithm fills — it works with counts rather than edges.

    Internal versus external fragmentation

    Internal — memory allocated to a process that it does not use, because allocation is in fixed-size units. A 5 KB process in a 4 KB-page system gets two pages and wastes 3 KB inside the last page. Paging suffers internal fragmentation, on average half a page per process.
    External — enough total free memory exists but it is split into non-contiguous holes, none big enough. Contiguous allocation and segmentation suffer this. Cures: compaction (shuffle everything to one end — expensive, and only possible with execution-time binding) or switch to paging, which does not require contiguity at all.

Shared pages let several processes map the same frame for read-only code, which is how a single copy of a library serves everyone.

    8. Virtual memory

    Virtual memory runs a program larger than physical memory by keeping only the pages currently needed in RAM. Demand paging brings a page in only when it is referenced; a valid/invalid bit in the page table marks which pages are resident.

    Page-fault handling, in order:

    1. The MMU finds the invalid bit set and traps to the OS.
    2. The OS saves the process state and checks whether the reference is legal — an illegal one becomes a segmentation fault.
    3. Find a free frame; if none is free, run the page-replacement algorithm to choose a victim, and write it out if it is dirty.
    4. Schedule a disk read of the required page into the frame.
    5. On completion, update the page table and the TLB, set the valid bit.
    6. Restart the instruction that faulted, from the beginning.

    Why the anomaly is possible at all. With 3 frames, pages 1 and 2 got evicted early — and were therefore reloaded early, which left them resident later when they were needed again. With 4 frames they survived longer, so they were still in the queue as the oldest entries when page 5 arrived, and were evicted at exactly the wrong moment. The deeper reason: with FIFO, the set of pages held by 4 frames is not guaranteed to contain the set held by 3.     Frame allocation. Equal — every process gets m/n frames. Proportional — frames in proportion to process size. Global replacement lets a process steal a frame from another (better throughput, but a process's fault rate then depends on others).     Thrashing — a process spends more time paging than executing. It begins when a process has fewer frames than its active working set; the resulting faults lower CPU utilisation, so the long-term scheduler admits more processes, which makes it worse — a positive feedback loop. Cures: the working-set model (track the pages referenced in the last Δ references and allocate that many frames; suspend a process if the sum of working sets exceeds the available frames) or page-fault frequency control (give a process more frames when its fault rate rises above an upper bound, take frames away when it drops below a lower bound).

    The inode is a deliberate bet on file-size distribution. A uniform scheme would have to charge every tiny file the cost of an index block. The structure is unbalanced because real workloads are unbalanced.
    The filename is not in the inode. The inode holds everything about the file — permissions, size, timestamps, block pointers — but not its name. The name lives in the directory entry, which is just a table of (name → inode number) pairs. This one design choice is why hard links work: two directory entries, possibly in different directories, can point at the same inode number, and neither is the "real" one. It is also why deleting a file is called unlink — you remove a directory entry, and the file's blocks are only freed when the inode's link count reaches zero. A soft (symbolic) link is different: a small file whose contents are a path string, so it breaks if the target is renamed, and it can cross file systems, which a hard link cannot.

    11. Protection and security

    Protection controls access by programs and users to system resources; security defends the system against external and internal attack. The guiding rule is the principle of least privilege.

    The access matrix, and the two ways to store it

    A protection domain is a set of (object, rights) pairs. The access matrix lays them all out: one row per domain, one column per object. Here is a small one from a banking system:

    12. Virtualisation

    Virtualisation runs several isolated systems on one machine. The distinction that gets examined is what is being duplicated, and a single picture settles it.

    Read the consequences straight off the picture. Each VM carries a whole guest OS, so it measures in gigabytes and takes tens of seconds to boot a kernel. A container carries only the application and its libraries, so it measures in megabytes and starts in under a second — there is no kernel to boot, because it is already running. Equally, the isolation is weaker: a container escape reaches the shared kernel, whereas a VM escape has to defeat the hypervisor and the CPU's virtualisation hardware. And a container cannot run Windows on a Linux host, because the kernel it plans to share is the wrong one.

    Three more single-process cases

    1. Self-request of a single-instance device. A process holds the only tape drive and requests a second one, or holds an exclusive file lock on a record and requests it again through a different code path.

    2. Waiting on a semaphore it must signal itself. A process executes wait(S) on a semaphore initialised to 0 that only it would later signal. It blocks and never reaches the signal.

    3. A single-threaded server calling itself. A process sends a synchronous request to a queue that it alone services, then blocks waiting for the reply it will never get round to producing.

    The distinction that earns the mark

    A deadlock is defined by a circular wait among the entities holding and requesting resources, not by a minimum headcount of processes. What genuinely is impossible is a deadlock with a single resource type having only one instance and no process holding it — with nothing held, hold-and-wait fails and no cycle can form.

    How systems prevent it. A recursive (reentrant) mutex records the owning thread and a lock count, so a re-lock by the same owner simply increments the count instead of blocking. The general defence is unchanged: acquire locks in a globally fixed order and never request a resource you already hold.

    (c) What happens if the producer's waits are swapped

    The broken version
    Producer:
    wait(mutex);   /* WRONG: lock the buffer FIRST */
    wait(empty);   /* then wait for a free slot    */
    add_to_buffer(item);
    signal(mutex);
    signal(full);

    1. The buffer fills up, so empty = 0.

    2. A producer runs. It executes wait(mutex) successfully — mutex becomes 0 and the producer now holds the lock.

    3. It then executes wait(empty). Since empty = 0, the producer blocks — while still holding the mutex.

    4. A consumer arrives to drain the buffer. Its first action is wait(full), which succeeds, then wait(mutex) — which blocks, because the producer holds it.

    5. Deadlock. The producer waits for a free slot that only the consumer can create; the consumer waits for the mutex that only the producer can release. All four Coffman conditions hold, and the circular wait is Producer → mutex → Consumer → empty → Producer.

    The rule this illustrates

    Never block on a condition while holding a lock. Acquire the counting semaphore first and the mutex last, and release in the reverse order. Stated generally: acquire locks in a fixed global order and hold them for the shortest possible time. Swapping the two signal calls at the end, by contrast, is harmless — neither can block.

    (d) Mutex versus semaphore

    See the full table in notes §5. The three points that carry the marks:

    • Ownership. A mutex is owned by the thread that locked it and only that thread may unlock it. A semaphore has no owner — any process may signal it, which is exactly what makes it usable for signalling between processes rather than just locking.
    • Value range. A mutex is binary by nature; a semaphore may count up to N and so can guard N identical resources.
    • Purpose. Mutex = mutual exclusion. Semaphore = synchronisation and resource counting. A binary semaphore resembles a mutex but is not the same thing, precisely because it lacks ownership — and therefore cannot support priority inheritance.
    (b) mutex = 1 for exclusion, empty = N and full = 0 for synchronisation; the producer does wait(empty) then wait(mutex). (c) Swapping them deadlocks the system: the producer blocks on a full buffer while holding the mutex the consumer needs to empty it.

    (iii) Starvation and aging

    Starvation (indefinite blocking) is a low-priority process never being scheduled because higher-priority processes keep arriving. Here P4, with the lowest priority, waited 15 of the 19 time units and ran last under both variants. In a live system where priority-1 and priority-2 jobs arrive continuously, P4 would never run at all.

    Aging fixes it by raising the priority of a process the longer it waits. Suppose the rule is decrease the priority number by 1 for every 5 time units spent waiting in the ready queue:

    Time waited05101520
    P4's effective priority54321

    After 20 units of waiting P4 has reached priority 1 and must outrank any newly arrived job, so it is guaranteed to be scheduled. Aging converts an unbounded wait into a bounded one — it supplies exactly the bounded waiting property that plain priority scheduling lacks. The apocryphal illustration is the IBM 7094 shut down at MIT in 1973, on which a job submitted in 1967 was found still waiting.

    (a) Thrashing

    Thrashing is the state in which a process spends more time servicing page faults than executing instructions. It begins when a process has fewer frames than its active working set: each reference evicts a page that is about to be needed again.

    The feedback loop that makes it catastrophic. Page faults make processes block on disk, so CPU utilisation drops. The long-term scheduler observes an idle CPU and concludes it should admit more processes. Those new processes take frames from the existing ones, so the fault rate rises further, utilisation drops further, and more processes are admitted. Utilisation falls to nearly zero while the disk saturates. The system is doing almost no useful work but appears extremely busy.

    (c) Recommendation for a core-banking database

    RAID 10. The reasoning, in order of weight:

    1. Write performance. A core-banking system is dominated by small random writes to the transaction log and data files. RAID 10 costs 2 I/Os per write against RAID 5's 4 and RAID 6's 6.

    2. Rebuild behaviour. Rebuilding a failed RAID 10 disk is a straight copy from its mirror. A second failure during that window destroys the array — a real and documented risk with large drives.

    3. Predictable latency. Parity calculation adds variable latency; mirroring does not. Transaction systems care about the tail latency, not just the average.

    4. The cost. 16 TB usable instead of 28 TB. For a system where an outage is measured in regulatory consequences rather than storage cost, this is the right trade. RAID 6 is the compromise if capacity genuinely matters, since it survives the second failure that kills RAID 5 during a rebuild.

    RAID is not backup

    RAID protects against disk hardware failure only. It does not protect against an accidental DELETE or DROP TABLE — the deletion is faithfully mirrored to every disk instantly; ransomware or malicious insiders, for the same reason; file-system or database corruption, which propagates; fire, flood or theft of the whole array; or the controller itself failing and writing garbage. A bank still needs point-in-time backups, tested restores, and an off-site or geographically separate disaster recovery copy. The Bangladesh Bank ICT Security Guideline requires exactly this separation between redundancy and backup.

    (a) Dining philosophers

    Five philosophers sit around a circular table. Between each adjacent pair lies one chopstick — five in total. A philosopher alternates between thinking and eating, and to eat must hold both the chopstick on the left and the one on the right. The problem models any situation where a process needs several exclusive resources at once.

    The naive solution — and why it fails
    semaphore chopstick[5] = {1, 1, 1, 1, 1};

Philosopher i:
  while (true) {
      think();
      wait(chopstick[i]);            /* pick up LEFT  */
      wait(chopstick[(i + 1) % 5]);  /* pick up RIGHT */
      eat();
      signal(chopstick[i]);
      signal(chopstick[(i + 1) % 5]);
  }

    Deadlock. If all five philosophers become hungry simultaneously and each picks up the chopstick on their left, all five semaphores are now 0. Every philosopher then waits for the chopstick on their right, which is held by their neighbour. The circular wait is P0 → c1 → P1 → c2 → P2 → c3 → P3 → c4 → P4 → c0 → P0, and all four Coffman conditions hold.

    Three correct solutions
    SolutionMechanismWhich condition it denies
    1. Allow at most four to sit A counting semaphore initialised to 4 admits philosophers to the table Circular wait — with four philosophers and five chopsticks, at least one can always get both
    2. Asymmetric ordering Odd-numbered philosophers take the left chopstick first; even-numbered take the right first. Equivalently, always take the lower-numbered chopstick first Circular wait — this is the general resource-ordering rule applied to chopsticks
    3. Pick up both atomically A monitor with a state array and a condition variable per philosopher; a philosopher may proceed only when both neighbours are not eating Hold and wait — a philosopher never holds one chopstick while waiting for the other

    Solution 3 is deadlock-free but not automatically starvation-free: two philosophers can alternate and permanently exclude the one between them. Adding a fairness rule — for example, a philosopher who has waited too long gets priority — is needed for a complete answer.

    (b) Readers-writers

    First readers-writers solution (reader priority)
    semaphore mutex = 1;    /* protects readcount            */

  wait(wrt);                       wait(mutex);
  /* ... write ... */              readcount++;
  signal(wrt);                     if (readcount == 1)
                                       wait(wrt);   /* first reader locks out writers */
                                   signal(mutex);

                                   /* ... read ... */

                                   wait(mutex);
                                   readcount--;
                                   if (readcount == 0)
                                       signal(wrt); /* last reader releases writers   */
                                   signal(mutex);

    How it works. Only the first reader competes for wrt; subsequent readers walk straight in, so many readers share the data concurrently. Only the last reader releases it. A writer needs wrt exclusively, so it excludes both other writers and all readers.

    Who starves. In this version, writers starve. As long as at least one reader is always inside, readcount never reaches zero, wrt is never signalled, and a waiting writer waits forever. The second readers-writers solution reverses the bias: once a writer is waiting, no new reader may start — which starves readers instead. A genuinely fair solution adds a turnstile semaphore that both parties must pass, so requests are served roughly in arrival order.

    This is exactly the trade-off a database makes with shared and exclusive row locks, and why real database engines implement lock queues with fairness rather than either naive version.

    (c) Priority inversion

    1. The scenario. Three tasks: H (high priority), M (medium), L (low).

      1. L acquires lock X and starts its critical section. 2. H becomes runnable, preempts L, and requests lock X → H blocks. 3. M becomes runnable. M has higher priority than L, so M preempts L. 4. L cannot run, so L cannot release X, so H cannot run. Result: H — the highest-priority task — is effectively waiting behind M, a task of LOWER priority that it does not even share a resource with. The priority ordering has been inverted.

    2. Why it matters. In a hard real-time system this causes missed deadlines. The famous case is the Mars Pathfinder lander in 1997, which repeatedly reset itself after a high-priority bus-management task was blocked by a low-priority meteorological task while medium-priority communications work ran. It was diagnosed and patched remotely.

    3. Priority inheritance — the fix. While a low-priority task holds a lock that a higher-priority task is waiting on, the holder temporarily inherits the waiter's priority. In the scenario above, L would be boosted to H's priority the moment H blocks, so M could not preempt it. L finishes its critical section quickly, releases X, drops back to its own priority, and H proceeds.

    4. Alternative — priority ceiling. Every lock is given a ceiling equal to the highest priority of any task that can acquire it; a task acquiring the lock immediately runs at that ceiling. This prevents the inversion rather than correcting it, and additionally prevents deadlock, at the cost of some unnecessary priority boosting.

    Note that priority inheritance requires the lock to have an owner, which is why it works with a mutex but not with a counting semaphore — the system cannot boost a holder it cannot identify.

    Why real systems use clock rather than true LRU

    1. Exact LRU needs work on every memory reference, not just on faults. The counter implementation writes a timestamp into the page-table entry on every access; the stack implementation moves an entry to the top of a doubly linked list on every access. Both mean extra memory writes for every single load and store the CPU executes.

    2. That cost cannot be paid in software. The MMU translates addresses in hardware without OS involvement; there is no hook where the OS could update an LRU list. Implementing it would require the hardware to maintain the ordering, which no mainstream architecture does — the cost in gates and in memory bandwidth is not considered worth it.

    3. Clock needs only one bit, set by hardware for free. Every MMU already maintains a reference bit as a side effect of translation. The OS reads and clears it only when a fault occurs — a few operations per fault instead of per access.

    4. The accuracy gap is small in practice. On real workloads with locality, clock's fault rate is within a few percent of LRU's. Paying a per-instruction cost to close a few-percent gap in a per-fault decision is a bad trade. Linux uses a two-list refinement of this idea; Windows uses a working-set variant.

    Enhanced second chance improves it further by using the pair (reference, modify) and preferring victims in the order (0,0), (0,1), (1,0), (1,1) — this avoids writing a dirty page to disk when a clean one is available, saving an entire disk write per eviction.

    Clock produces 14 page faults on this string, against 15 for FIFO, 12 for LRU and 9 for optimal. It is used in practice because it needs only one hardware-maintained reference bit and does work only on a fault, whereas true LRU would require bookkeeping on every memory access.

    What happens on read(fd, buf, n):

    1. The user program calls the C library wrapper read(), which places the system-call number and the three arguments in registers.

    2. The wrapper executes a trap instruction (syscall on x86-64, svc on ARM). The hardware switches the mode bit to kernel mode and jumps to a fixed handler address in the kernel — the user program cannot choose where it lands.

    3. The kernel saves the user context, looks up the call number in the system-call table, and validates the arguments: is fd an open file for this process, does buf point into this process's own address space, is n sane? This validation is the security boundary.

    4. The kernel checks the buffer cache. On a hit it copies the data out immediately. On a miss it issues a disk request, marks the process Waiting, and calls the scheduler — another process now runs.

    5. When the disk interrupt arrives, the driver copies the data into the kernel buffer and moves the process from Waiting to Ready.

    6. When rescheduled, the kernel copies the data from the kernel buffer to the user's buf, sets the return value to the byte count, restores the user context, switches the mode bit back to user mode, and returns to the instruction after the trap.

    Why the separation exists. Without it, any program could write directly to the disk controller and destroy another user's files, disable interrupts and monopolise the CPU forever, read another process's memory including its passwords and keys, or overwrite the kernel itself. Dual-mode operation makes those instructions trap instead of execute when the mode bit says "user", which is what turns the OS from a helpful library into an enforceable authority. The cost is that every service request pays a mode-switch, which is why reducing the number of system calls — through buffering, batching and memory-mapped I/O — is a standard performance technique.

    (a) Multiprogramming and multitasking give concurrency on one CPU; multiprocessing gives true parallelism on several; multithreading divides one process. (b) Buffering overlaps I/O with computation of the same job; spooling overlaps across different jobs. (c) A system call traps into kernel mode through a fixed handler and returns via a mode switch. (d) The separation exists to make privileged instructions unavailable to ordinary programs.
    Given
    • Rotational speed = 7200 revolutions per minute
    • Average seek time = 5 ms
    • Sustained transfer rate = 100 MB/s = 100 × 10⁶ bytes per second
    Disk access time = seek time + rotational latency + transfer time

    (a) Average rotational latency

    1. Find the time for one full rotation.

      7200 RPM = 7200 / 60 = 120 revolutions per second Time for 1 revolution = 1 / 120 s = 0.008333 s = 8.333 ms

    2. On average the required sector is half a rotation away.

      Average rotational latency = 8.333 / 2 = 4.167 ms

    (b) Reading one 4 KB block

    1. Transfer time for 4096 bytes at 100 MB/s.

      Transfer time = 4096 / (100 × 10⁶) s = 4.096 × 10⁻⁵ s = 0.041 ms

    2. Total.

      Access time = 5 ms + 4.167 ms + 0.041 ms = 9.208 ms ≈ 9.21 ms

    3. Random I/O operations per second.

      IOPS = 1000 ms / 9.208 ms = 108.6 ≈ 109 IOPS

    Seek5.000 ms54.3%
    Rotational latency4.167 ms45.3%
    Transfer0.041 ms0.4%

    99.6% of the time is spent getting to the data, not reading it. That single figure justifies the whole of disk scheduling, the buffer cache, read-ahead, contiguous allocation and defragmentation. It also explains why a database index — which turns many random reads into few — is worth its storage cost many times over.

    (c) Reading a 1 MB contiguous file

    1. Because the file is contiguous, the head seeks once and the platter's rotation is paid once; the rest is pure transfer.

      Transfer time = 1 × 10⁶ / (100 × 10⁶) s = 0.01 s = 10 ms Total = 5 ms (seek) + 4.167 ms (latency) + 10 ms (transfer) = 19.167 ms

    2. Effective throughput.

      Throughput = 1 MB / 19.167 ms = 1 / 0.019167 MB per second = 52.2 MB/s

    3. Why only 52% of the rated speed? The 100 MB/s figure is the rate at which bits stream off the platter once the head is in position. The 9.167 ms of seek plus latency is fixed overhead paid before a single byte moves, and for a 1 MB read that overhead is nearly as large as the transfer itself. The larger the read, the more the overhead amortises: a 100 MB contiguous read takes 9.167 + 1000 = 1009 ms, giving 99.1 MB/s — essentially the rated figure. Conversely, if that same 1 MB were fragmented into 256 scattered 4 KB blocks it would cost 256 × 9.208 = 2357 ms, a throughput of 0.42 MB/s — 123 times slower. That contrast is the entire argument for contiguous allocation and defragmentation.

    OS mechanisms that become irrelevant or must change:

    • Disk scheduling algorithms lose their purpose. SSTF, SCAN, LOOK and C-LOOK all exist to minimise head movement, and there is no head. Linux therefore offers a none/noop scheduler for SSDs, which simply passes requests through, and the device's own controller reorders them internally.
    • Defragmentation becomes harmful. It provides no benefit — random access is as fast as sequential — while consuming a share of the finite number of write cycles each flash cell can endure.
    • Contiguous allocation matters far less as a performance strategy, though it still helps by reducing metadata.
    • New concerns appear that HDDs never had: wear levelling spreads writes evenly across cells; the TRIM command tells the drive which blocks the file system has freed so it can erase them in advance; and write amplification means a small logical write may cause a much larger physical erase-and-rewrite of a whole block.

(c) 1 MB contiguous read = 19.17 ms, an effective 52.2 MB/s, because 9.17 ms of fixed seek and rotation overhead is paid before any transfer begins. (d) An SSD removes seek and rotational latency entirely, which makes disk-scheduling algorithms and defragmentation pointless.
