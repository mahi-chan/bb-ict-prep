    1. Foundations

    Data structure
    A concrete arrangement of data in memory together with the operations allowed on it.
    Abstract Data Type
    The logical specification only — what operations exist and what they mean, not how they are stored. Stack is an ADT; an array-based stack is a data structure.
    Linear vs non-linear
    Linear: elements form one sequence (array, linked list, stack, queue). Non-linear: one element may have many successors (tree, graph).
    Static vs dynamic
    Static: size fixed at compile time (array). Dynamic: grows and shrinks at run time (linked list, dynamic array).
    Time complexity
    Growth of the number of primitive operations with input size n, stated asymptotically.
    Space complexity
    Total memory = input space + auxiliary space. Quoted complexity usually means auxiliary space.

    Best, average and worst case are three different inputs of the same size, not three different sizes. Linear search for a key: best case the key is first, O(1); worst case last or absent, O(n); average, with the key equally likely at any of n positions, (n+1)/2 comparisons, still O(n).

    What the notation actually buys you

    O(n) versus O(log n) looks like abstract bookkeeping until it is given a number. Suppose a branch holds 1,000 customer records and you need to find one account. Here is what each structure costs, in real comparisons:

    Stored asComparisons to find one recordWorked outCost to insert a new record
    Unsorted array 1,000 worst · 500 average check every element O(1) — append at the end
    Sorted array 10 ⌊log₂1000⌋ + 1 = 9 + 1 O(n) — shift ~500 elements to make room
    Balanced BST 10 tree height ≈ log₂1000 ≈ 10 O(log n) — 10 comparisons, no shifting
    Hash table 1 compute the slot, look O(1) average
    The point1,000 comparisons versus 10 — a hundredfold difference on the same data
    At 1 millionlinear search needs 1,000,000; binary search needs 20. The gap widens as the data grows — which is the whole reason complexity is measured asymptotically.
    Butthe sorted array is fastest to search and among the worst to update. There is no best structure — only the right trade for the operation you perform most.

    That last line is the reason this subject exists. Every structure below buys speed in one operation by paying for it in another, and exam questions are usually asking you to name the trade.

    2. Arrays and address calculation

    An array stores elements of one type in contiguous memory, so the address of any element is computable in O(1) — that constant-time formula is the whole reason arrays are fast, and it is a recurring exam question.

    Where the formula comes from

    Memory is one long line of numbered bytes. An array is simply a block of that line, and because every element is the same width and they sit shoulder to shoulder, you never have to search for one — you can work out its address. Take five 4-byte integers starting at address 1000:

    That is the entire formula. "Two cells past the start" generalises to i − LB, because if the array is declared A[1..5] then A[1] is the zeroth cell, not the first:

    Address(A[i]) = Base + w × (i − LB)
    Two dimensions, but memory is still one line

    A matrix is a convenient fiction. Memory has no rows or columns, so a 2-D array must be flattened into a single line — and there are exactly two sensible ways to do it. Take a 3 × 4 array:

    Now the formulas are just a description of those two pictures. To reach a12 in the row-major strip you skip 1 whole row of 4, then 2 more cells. In the column-major strip you skip 2 whole columns of 3, then 1 more cell:

    Row-major:    Address(A[i][j]) = Base + w × [ (i − LR) × NC + (j − LC) ] Column-major: Address(A[i][j]) = Base + w × [ (j − LC) × NR + (i − LR) ]

    With base 1000 and 4-byte elements, the two answers for that same element:

    Row-major1000 + 4 × [ 1 × 4 + 2 ] = 1000 + 4 × 6 = 1024
    Col-major1000 + 4 × [ 2 × 3 + 1 ] = 1000 + 4 × 7 = 1028
    Checkpositions 6 and 7 in the two strips above — count the cells and confirm it by eye before trusting the arithmetic.
    Where marks are lost

    Row-major multiplies the row offset by the number of columns; column-major multiplies the column offset by the number of rows. Reading the array bounds as [1..8, 1..10] and then using LB = 0 is the other standard slip. C uses row-major; FORTRAN and MATLAB use column-major.

    Sparse matrices

    A matrix in which most entries are zero. Storing all m × n cells wastes space, so use the 3-tuple (triplet) representation: a table with one row per non-zero element holding (row, column, value), preceded by a header row holding (rows, columns, non-zero count). A 5 × 6 matrix with 6 non-zero entries needs 7 × 3 = 21 cells instead of 30. The alternative is a linked-list representation with one node per non-zero entry.

    Insertion and deletion cost

    Inserting at position k in an array of n elements shifts n − k elements right; deleting shifts n − k left. Averaged over all positions this is n/2 moves, hence O(n). This single fact is the argument for linked lists.

    The four routines that get asked

    C — reverse, middle, cycle detection, merge
    struct Node { int data; struct Node *next; };

/* 1. Reverse a singly linked list — iterative, O(n) time, O(1) space */
struct Node *reverse(struct Node *head) {
    struct Node *prev = NULL, *curr = head, *next = NULL;
    while (curr != NULL) {
        next = curr->next;   /* remember the rest of the list  */
        curr->next = prev;   /* flip this link backwards       */
        prev = curr;         /* slide the two pointers forward  */
        curr = next;
    }
    return prev;             /* prev is the old last node       */
}

/* 2. Middle node — slow/fast pointers, one pass */
struct Node *middle(struct Node *head) {
    struct Node *slow = head, *fast = head;
    while (fast != NULL && fast->next != NULL) {
        slow = slow->next;        /* one step  */
        fast = fast->next->next;  /* two steps */
    }
    return slow;   /* for even length this returns the second middle */
}

/* 3. Floyd's cycle detection — the tortoise and the hare */
int hasCycle(struct Node *head) {
    struct Node *slow = head, *fast = head;
    while (fast != NULL && fast->next != NULL) {
        slow = slow->next;
        fast = fast->next->next;
        if (slow == fast) return 1;   /* they can only meet in a loop */
    }
    return 0;
}

/* 4. Merge two sorted lists into one sorted list */
struct Node *merge(struct Node *a, struct Node *b) {
    struct Node dummy, *tail = &dummy;
    dummy.next = NULL;
    while (a && b) {
        if (a->data <= b->data) { tail->next = a; a = a->next; }
        else                    { tail->next = b; b = b->next; }
        tail = tail->next;
    }
    tail->next = (a != NULL) ? a : b;   /* attach whatever is left */
    return dummy.next;
}
    Why Floyd's algorithm must work

    If a cycle of length L exists, once both pointers are inside it the gap between them changes by exactly one node per iteration. A gap that decreases by 1 each step from at most L−1 must reach 0 within L steps, so they meet. Total time O(n), extra space O(1).

    4. Stack

    LIFO — last in, first out. Operations: push, pop, peek/top, isEmpty, isFull, all O(1). Overflow is a push onto a full array stack; underflow is a pop from an empty stack. A linked implementation never overflows until heap memory runs out.

    Applications

    • Expression conversion: infix → postfix and infix → prefix.
    • Postfix (and prefix) expression evaluation.
    • Parenthesis / bracket matching in compilers.
    • The function call stack — return addresses, parameters, locals; recursion depends on it.
    • Undo/redo, browser back button.
    • Backtracking — maze solving, N-queens, DFS (iterative form).
    • Tower of Hanoi and other recursive procedures.
    Why postfix exists at all

    We write 2 + 3 × 4 and know the answer is 14, not 20 — because we have memorised that × binds tighter than +. A machine has no such intuition, and brackets only push the problem around. Postfix notation removes the ambiguity entirely: 2 3 4 × + has exactly one reading, needs no precedence rules and no brackets, and can be evaluated by a stack in a single left-to-right pass. Converting infix to postfix is how a compiler gets from what a human typed to something it can execute.

    Watch the stack during a conversion

    Convert A + B * C. The output collects operands immediately; the stack holds operators that are waiting to find out whether something higher-precedence comes along.

    Why the stack does the work. An operator cannot be written to the output the moment you read it, because a higher-precedence operator might still be coming — in A + B * C the + has to wait for B * C to be resolved first. The stack is exactly the right structure for "wait until something more urgent is finished", because the most recently pushed operator is the most urgent, and it is the first one back off.

    With that picture in mind, the rules below are just its description. Write them out in this order in an answer:

    Infix → postfix, the algorithm to write in the answer

    1. Scan the infix expression left to right.
    2. Operand → append it straight to the output.
    3. ( → push onto the stack.
    4. ) → pop and output until ( is popped; discard both brackets.
    5. Operator → while the stack top is an operator of higher precedence, or of equal precedence and the operator is left-associative, pop it to the output. Then push the new operator.
    6. End of input → pop the whole stack to the output.
    Precedence and associativity
    OperatorPrecedenceAssociativity
    ^ (exponent)3 (highest)Right to left
    * / %2Left to right
    + −1Left to right

    Infix → prefix is the same machine run backwards: reverse the infix string, swap every ( with ), convert to postfix treating ^ as left-associative and * / + − as right-associative, then reverse the result.

    Postfix evaluation: scan left to right; push operands; on an operator pop two values — the second pop is the left operand — apply, push the result. One value remains at the end. Prefix evaluation is identical but scanning right to left, with the first pop as the left operand.

    Tower of Hanoi

    Moves obey T(n) = 2T(n−1) + 1 with T(1) = 1, giving T(n) = 2ⁿ − 1. For n = 5, 31 moves; for n = 10, 1023. The recursion is move n−1 to spare, move the largest to destination, move n−1 onto it.

    5. Queue

    FIFO — first in, first out. Insert at rear (enqueue), remove from front (dequeue).

    The defect that circular queues exist to fix

    Put a queue in a plain array with a front index and a rear index. Enqueue five items, then dequeue three. Both indices only ever move forward, so they have crawled towards the end of the array — and now the queue insists it is full while three perfectly good slots sit empty behind it:

    Linearrear = rear + 1 → 4 + 1 = 5 ✗ out of bounds
    Circularrear = (rear + 1) % SIZE → (4 + 1) % 5 = 0 ✓ reuses slot 0

    Nothing about the array changed. The only difference is that the index arithmetic is done modulo the array size, which makes position 4 and position 0 neighbours. That single % is the whole of the circular queue.

    Circular queue conditions Empty: front == −1 (sentinel convention) Full: (rear + 1) % SIZE == front Enqueue: if empty → front = rear = 0, else rear = (rear + 1) % SIZE Dequeue: if front == rear → front = rear = −1, else front = (front + 1) % SIZE Count: (rear − front + SIZE) % SIZE + 1 (when not empty)

    Watch which convention the question uses. With the front == −1 sentinel above, emptiness is flagged separately from the pointer positions, so all SIZE slots are usable — a size-5 array holds 5 items. The other common convention has no sentinel and calls the queue empty when front == rear; that collides with the full condition unless one slot is deliberately left unused, so a size-5 array then holds only 4. Keeping an explicit count variable removes the ambiguity entirely.

    Queue variants
    VariantBehaviourUse
    Linear queuePlain FIFO, space not reusedTeaching example
    Circular queueIndices wrap with % SIZEBuffers, round-robin scheduling
    DequeInsert and delete at both endsSliding-window problems, undo history
    Priority queueHighest priority leaves first, not the oldestCPU scheduling, Dijkstra, Huffman

    Queue using two stacks. Enqueue pushes onto S1. Dequeue: if S2 is empty, pop everything from S1 into S2 (which reverses the order), then pop S2. Each element is moved at most once each way, so the amortised cost is O(1) even though a single dequeue can cost O(n).

    Stack using two queues. Make push costly: enqueue the new item into the empty Q2, move all of Q1 behind it, then swap the names. Push O(n), pop O(1).

    Applications: CPU and disk scheduling, print spooling, keyboard buffers, BFS, call-centre queues, network packet queues, producer–consumer buffers.

    Representation

    Array (implicit). For a node at index i (0-based): left child 2i+1, right child 2i+2, parent ⌊(i−1)/2⌋. With 1-based indexing: 2i, 2i+1, ⌊i/2⌋. Perfect for complete trees (heaps); wasteful for skewed trees, which need 2ⁿ − 1 slots for n nodes.

    Linked. Each node holds left, data, right. No waste, but n+1 of the 2n pointers are NULL — which is exactly what threaded binary trees exploit.

    Traversals

    To traverse a tree is to visit every node exactly once, in some definite order. A list has only one sensible order, front to back. A tree does not: standing at any node you have three things to deal with — the node itself, its left subtree and its right subtree — and you must choose which to handle first.

    Left is always dealt with before right. So the only real decision is when you handle the node itself, and there are three answers: before the subtrees, between them, or after them. Those three answers are the three traversals, and the names say which one you picked.

    The prefix tells you where the root goes. Preorder — root before the subtrees. Inorder — root in between them. Postorder — root after them. Left before right in all three, always. If you remember only this, you can derive all three orders without memorising them separately.

    Everything below uses this one tree, so the three outputs can be compared directly:

    Preorder, worked in full

    The rule is visit the node, then go left, then go right. Apply it at every node, including the ones you reach on the way down. Follow it literally:

    Preorder — the recursion unfolding, one move at a time
    #At nodeWhat the rule says to doOutput so far
    1Fvisit F, then go into F's left subtreeF
    2Bvisit B, then go into B's left subtreeF B
    3Avisit A; A has no children, so back up to BF B A
    4Bleft is finished — now go into B's right subtreeF B A
    5Dvisit D, then go into D's left subtreeF B A D
    6Cvisit C; no children, back up to DF B A D C
    7ED's right subtree: visit E; no children, back upF B A D C E
    8—B is finished, so F's left subtree is finished; go rightF B A D C E
    9Gvisit G; G has no left child, so go straight rightF B A D C E G
    10Ivisit I, then go into I's left subtreeF B A D C E G I
    11Hvisit H; no children; everything is now finishedF B A D C E G I H

    Step 8 is the one worth staring at. Nothing is printed — it is pure backing-up. Most traversal mistakes are made there, by forgetting to return all the way to F before starting on G.

    The same tree, the other two orders

    Only the position of the node's own visit changes. Work the left subtree of F first in each case and the pattern is obvious:

    Preorder root, left, right F then (B A D C E) then (G I H) → F B A D C E G I H
    Inorder left, root, right (A B C D E) then F then (G H I) → A B C D E F G H I
    Postorder left, right, root (A C E D B) then (H I G) then F → A C E D B H I G F
    Notice F is first in preorder, in the middle in inorder, and last in postorder — exactly as the names promise. The root of any tree is always the first symbol of its preorder and the last of its postorder, which is what makes tree reconstruction possible.
    Why inorder came out alphabetical. That was not luck — this tree is a BST on letters. In a BST everything in the left subtree is smaller than the node and everything in the right subtree is larger. Inorder says all of left, then me, then all of right — which is everything smaller, then me, then everything larger. That is the definition of sorted order, applied at every node. So the inorder traversal of a BST is always sorted, and this is the standard way to test whether a tree really is a BST.
    Level order is a different animal

    The three above are all depth-first: they dive to the bottom of one branch before touching the next. Level order is breadth-first — it reads the tree row by row, the way you would read text on a page:

    Level 0F
    Level 1B G
    Level 2A D I
    Level 3C E H
    Level orderF B G A D I C E H

    This one cannot be written with plain recursion, and that is the point of it. Recursion naturally goes deep; to go wide you must remember the nodes you have seen but not yet dealt with, in the order you met them — which is a queue. The other three use a stack, whether you supply it yourself or let the function-call mechanism supply it for you.

    Recap — now that you have seen each one run

    C — recursive and iterative inorder, plus level order
    struct Node { int data; struct Node *left, *right; };

void inorderRec(struct Node *r) {
    if (r == NULL) return;
    inorderRec(r->left);
    printf("%d ", r->data);
    inorderRec(r->right);
}

/* Iterative inorder — an explicit stack replaces the call stack */
void inorderIter(struct Node *root) {
    struct Node *stack[100], *curr = root;
    int top = -1;
    while (curr != NULL || top != -1) {
        while (curr != NULL) { stack[++top] = curr; curr = curr->left; }
        curr = stack[top--];
        printf("%d ", curr->data);
        curr = curr->right;
    }
}

/* Level order — a queue, one level at a time */
void levelOrder(struct Node *root) {
    struct Node *q[100];
    int front = 0, rear = 0;
    if (root == NULL) return;
    q[rear++] = root;
    while (front < rear) {
        struct Node *n = q[front++];
        printf("%d ", n->data);
        if (n->left)  q[rear++] = n->left;
        if (n->right) q[rear++] = n->right;
    }
}
    Reconstructing a tree from two traversals

    Inorder + preorder or inorder + postorder determine the tree uniquely. Preorder + postorder do not — they cannot distinguish a single left child from a single right child, so they are unique only for full binary trees.

    Method: the first item of preorder (or the last of postorder) is the root. Find it in the inorder list; everything to its left is the left subtree, everything to its right is the right subtree. Recurse on each side. Worked in solved question 5.

    Expression trees and threaded trees

    In an expression tree leaves are operands and internal nodes are operators. Inorder gives infix (needing brackets), preorder gives prefix, postorder gives postfix. Evaluating it is a postorder traversal.

    A threaded binary tree replaces NULL pointers with "threads" pointing to the inorder predecessor (left NULL) and inorder successor (right NULL). Result: inorder traversal without recursion and without a stack, in O(1) extra space. Single-threaded uses the right NULLs only; double-threaded uses both.

    7. Binary search tree

    An ordinary binary tree puts keys wherever there is room, so finding one means checking all n of them. A binary search tree fixes the position of every key by one rule, and that rule is what lets you throw away half the tree at every step.

    The rule. At every node: everything in the left subtree is smaller than that node, and everything in the right subtree is larger. Not just the immediate children — the entire subtree beneath. Every operation below is a consequence of this one sentence.
    Building one, key by key

    Insert 40, 25, 60, 15, 30, 50, 70 into an empty tree. Each key starts at the root and walks down: smaller means go left, larger means go right. When it walks off the end of the tree, that spot is where it belongs.

    Searching is the same walk

    Search uses the identical rule as insertion, which is the whole reason for building it this way: compare, move one way, repeat.

    Deleting — and why there are exactly three cases

    A deletion has to leave the rule true for every node that remains. How difficult that is depends only on how many children the doomed node has — which is why there are three cases and not one. Take them in turn on the tree above.

    1. Case 1 — a leaf. Delete 15.

      15 has no children, so nothing hangs off it and nothing depends on it. Remove it, set 25's left pointer to NULL, and no other node can even tell.

      Tree now40( 25(–, 30), 60(50, 70) )
    2. Case 2 — one child. Delete 25.

      After the previous step 25 has only a right child, 30. Everything in that subtree was already known to be smaller than 40, so lifting it up into 25's place cannot violate anything — 40 simply adopts 30 directly.

      Tree now40( 30, 60(50, 70) )
    3. Case 3 — two children. Delete 40, the root.

      This is the case that needs thought. 40 has two subtrees but its parent slot can hold only one pointer, so neither child can just be promoted. The trick is to not remove the node at all: overwrite its key with the one value that may legally sit there, then delete that value from where it came from.

      Which value qualifies? It has to be larger than everything on the left and smaller than everything on the right — so it is the smallest key in the right subtree, the inorder successor.       Stepdelete the original 50 — it is a leaf, so this is just Case 1 again
      Result50( 30, 60(–, 70) )

      The successor is always easy to remove: being the leftmost node of its subtree it cannot have a left child, so it is always Case 1 or Case 2. Case 3 therefore collapses into an earlier case instead of recursing forever — that is why three cases are enough.

    Successor and predecessor, stated properly
    Inorder successor The next key upward. If the node has a right subtree, it is that subtree's leftmost node. If not, walk up to the lowest ancestor you reached by a left link.
    Inorder predecessor The next key downward — the mirror image: the left subtree's rightmost node, or the lowest ancestor reached by a right link.
    Minimum and maximum Follow left pointers to the end, or right pointers to the end. No key comparisons are needed at all.
    k-th smallest Inorder traversal, stopping at the k-th visit — O(h + k). Keeping a subtree-size count in each node brings it down to O(h).

    Either the successor or the predecessor may be used in Case 3 — both are correct. Using 30, the predecessor, would have produced 30( –, 60(50, 70) ) instead, which is equally valid. State which convention you are using and keep to it.

    Validating a BST — the trap. Checking only left < node < right at each node is not enough, because the rule constrains whole subtrees rather than immediate children. Take root 40 with left child 25, and give 25 a right child of 90. Every local check passes — 25 < 40 ✓, 90 > 25 ✓ — yet 90 sits inside 40's left subtree while being larger than 40. The correct test carries a permitted range down the tree (25 must lie in (−∞, 40), so its right child must lie in (25, 40)), or simply confirms that the inorder traversal comes out strictly increasing.
    What it costs, and how it goes wrong
    All opssearch, insert and delete are each O(h), where h is the height
    Balancedh ≈ log₂n — the 7-node tree above has height 2, so at most 3 comparisons
    Degenerateh = n − 1 — the tree becomes a linked list and every operation is O(n)

    Insert the same seven keys in ascending order — 15, 25, 30, 40, 50, 60, 70 — and each one is larger than the last, so each one goes right. The result is a straight chain of height 6 with no branching anywhere: identical keys, identical rule, and searching now costs 7 comparisons instead of 3. Nothing in the BST rule prevents this, which is precisely why AVL and red-black trees exist — they add rebalancing so the height cannot run away.

    8. Balanced and multiway trees

    AVL trees

    Named for Adelson-Velsky and Landis. Every node stores a balance factor:

    BF(node) = height(left subtree) − height(right subtree), BF ∈ {−1, 0, +1}

    If an insertion pushes some node's BF to +2 or −2, rebalance at the lowest such node. Four cases, identified by the direction of the first two steps down towards the newly inserted key:

    The four rotation cases
    CaseDetected whenFix
    LLBF = +2 and left child's BF = +1One right rotation about the unbalanced node
    RRBF = −2 and right child's BF = −1One left rotation about the unbalanced node
    LRBF = +2 and left child's BF = −1Left rotation on the left child, then right rotation on the node
    RLBF = −2 and right child's BF = +1Right rotation on the right child, then left rotation on the node
    Reading balance factors off a real tree

    Before you can pick a rotation you have to find the node that is broken. Work bottom-up and stop at the first node whose balance factor reaches ±2 — that is the one to rotate about, not the root. Insert 30, 10, 20:

    Node 20no children → height 0 → BF = (−1) − (−1) = 0 ✓ balanced
    Node 10left empty (h = −1), right is 20 (h = 0) → BF = −1 − 0 = −1 ✓ still legal
    Node 30left subtree h = 1, right empty (h = −1) → BF = 1 − (−1) = +2 ✗ BROKEN — rotate here

    Now identify which of the four cases it is. Node 30 has BF = +2, so it is left-heavy — the first letter is L. Its left child, 10, has BF = −1, so that node is right-heavy — the second letter is R. Left then right: this is the LR case, and it needs two rotations, not one.

    Why a single rotation fails here. Rotating right about 30 straight away would move 10 up and 30 down — but 20, being in 10's right subtree, simply swaps sides and the tree stays just as lopsided. A single rotation only works on a straight chain (LL or RR). When the path zig-zags, the first rotation exists purely to straighten it, and the second one does the actual balancing. That is the whole reason LR and RL need two rotations while LL and RR need one.

    Height of an AVL tree with n nodes is at most 1.44 log₂(n+2), so search, insert and delete are all O(log n). Insertion needs at most one rotation (single or double); deletion may need up to O(log n) rotations up the path.

    Red-black tree properties
    1Every node is red or black.
    2The root is black.
    3Every leaf (NIL) is black.
    4A red node's children are both black — no two reds in a row.
    5Every path from a node to its descendant NILs contains the same number of black nodes (equal black height).

    Consequence: the longest path is at most twice the shortest, so height ≤ 2 log₂(n+1). Red-black trees are less rigidly balanced than AVL — slower lookups, faster insert and delete — which is why language libraries (C++ map, Java TreeMap) use red-black while lookup-dominated workloads prefer AVL.

    B-tree and B+ tree

    A B-tree of order m is a balanced multiway search tree: every node holds up to m−1 keys and m children; every node except the root holds at least ⌈m/2⌉−1 keys; all leaves are at the same level. Height is O(log_m n), and because m is chosen so a node fills one disk block, a lookup costs only a handful of disk reads.

    A B+ tree keeps all data in the leaves and uses internal nodes purely as an index, then links the leaves in a chain. Two consequences, and both are the answer to "why do databases use B+ trees":

    • Internal nodes hold keys only, so more keys fit per block, so the tree is shorter and fewer disk I/Os are needed.
    • The linked leaf chain makes range queries and full scans sequential — BETWEEN, ORDER BY and index scans all become cheap. A B-tree would have to traverse up and down repeatedly.

    A 2-3 tree is the special case m = 3: every internal node has 2 or 3 children, holds 1 or 2 keys, and all leaves are on one level.

    9. Heaps and priority queues

    A binary heap is a complete binary tree — every level full except possibly the last, which fills left to right — obeying one rule: in a min-heap every parent is ≤ both of its children, so the smallest key is forced to the root. A max-heap is the same with the comparison reversed.

    Note what the rule does not say. There is no ordering between siblings, and no ordering across the tree. A heap is not sorted; it only guarantees that the extreme value is at the top. That weaker promise is what makes it so much cheaper to maintain than a BST, and it is exactly the promise a priority queue needs.

    The array is the tree

    Because a heap is always complete, it has no gaps — so it can be poured into an array row by row with no pointers at all, and the tree structure is recovered purely by arithmetic on the indices:

    Nodes near the leaves are the numerous ones, and they sift down the shortest distance. There are at most ⌈n/2^(h+1)⌉ nodes of height h, each costing O(h), so the total is n · Σ h/2^(h+1) = 2n = O(n). Inserting n keys one at a time, by contrast, really does cost O(n log n).

    Priority queue. The heap is the standard implementation. Unsorted array: insert O(1), extract O(n). Sorted array: insert O(n), extract O(1). Binary heap: both O(log n) — the best balance, which is why Dijkstra, Prim, Huffman coding and CPU schedulers all use it.

    C — min-heapify and build-min-heap
    void swap(int *a, int *b) { int t = *a; *a = *b; *b = t; }

/* Sift down: assume both subtrees of i are heaps, fix node i */
void minHeapify(int A[], int n, int i) {
    int smallest = i;
    int l = 2 * i + 1, r = 2 * i + 2;
    if (l < n && A[l] < A[smallest]) smallest = l;
    if (r < n && A[r] < A[smallest]) smallest = r;
    if (smallest != i) {
        swap(&A[i], &A[smallest]);
        minHeapify(A, n, smallest);   /* the violation may have moved down */
    }
}

/* Build: heapify every non-leaf, bottom-up. O(n) overall. */
void buildMinHeap(int A[], int n) {
    for (int i = n / 2 - 1; i >= 0; i--)
        minHeapify(A, n, i);
}

    10. Hashing

    An array can reach any element instantly — but only if you already know the index. Hashing removes that condition: it computes the index from the key itself. Store account number 4021 by working out where 4021 belongs, and later find it by doing the identical calculation. No searching at all.

    Watch one table being filled

    Take a table of m = 7 slots and the simplest possible hash function, h(k) = k mod 7. Insert 15, 11, 27:

    Key 1515 mod 7 = 1 (7 × 2 = 14, remainder 1) → slot 1
    Key 1111 mod 7 = 4 (7 × 1 = 7, remainder 4) → slot 4
    Key 2727 mod 7 = 6 (7 × 3 = 21, remainder 6) → slot 6
    Slot0123456

    Three keys, three slots, no trouble. Finding 11 later costs one calculation and one array read — no comparisons with 15 or 27 at all. That is the O(1) everyone quotes.

    Now insert 8, and the problem appears
    Key 88 mod 7 = 1 → slot 1
    Problemslot 1 already holds 15. This is a COLLISION.
    Collisions are not a flaw, they are arithmetic. Account numbers are effectively unlimited; the table has 7 slots. Mapping many possible keys into few slots must send some of them to the same place — the pigeonhole principle. So the interesting question is never "how do I avoid collisions" but "what do I do when one happens". Every hash table needs an answer, and the choice of answer is what distinguishes the schemes below.
    Three ways to resolve it, on identical data

    Continue inserting 8, 22, 30 into the table above — a deliberately awkward set, since 8 mod 7 = 1 and 22 mod 7 = 1 both land on 15, and 30 mod 7 = 2 lands next door.

    3 · Double hashing — let the key choose its own step size

    Instead of always stepping by 1, step by an amount computed from the key itself. Use h₂(k) = 5 − (k mod 5), which always yields 1 to 5 and so is never zero.

    Quadratic probing sits between the two: it probes h(k)+1², h(k)+2², h(k)+3²… which breaks up runs, but every key with the same home slot still follows the same jump pattern — secondary clustering.     11. Graphs

    Graph
    G = (V, E) — a vertex set and an edge set.
    Directed / undirected
    Edges have a direction, or not. An undirected edge counts once in |E| but appears twice in an adjacency matrix.
    Degree
    Edges touching a vertex. Handshaking lemma: Σ deg(v) = 2|E|. Directed graphs split it into in-degree and out-degree.
    Path / cycle
    A walk with no repeated vertex; a path whose ends coincide.
    Connected
    Every vertex reachable from every other. Directed version: strongly connected.
    Complete graph Kn
    Every pair joined: n(n−1)/2 edges undirected, n(n−1) directed.
    Dense / sparse
    |E| ≈ |V|² versus |E| ≈ |V| — this decides matrix vs list.
    Spanning tree
    A subgraph that is a tree touching every vertex — exactly |V| − 1 edges, no cycle.
    One graph, stored two ways

    A graph has no natural layout in memory the way an array does, so it has to be encoded. There are two standard encodings, and the choice between them is one of the few genuine engineering decisions in this subject. Take this five-vertex graph:

    MatrixV² = 5² = 25 cells, regardless of how few edges exist
    ListV + 2E = 5 + 10 = 15 units
    TradeThe matrix answers "is 1 joined to 4?" in one lookup — read cell [1][4]. The list must walk 1's neighbours to find out. The matrix buys that speed with space it wastes on every absent edge.
    Rulesparse graph (E ≈ V) → list · dense graph (E ≈ V²) → matrix. Real networks are almost always sparse, so the list is the usual choice.
    The two traversals, on that graph

    Both start somewhere and reach everything connected to it. They differ only in which unexplored vertex they pick next — and that single difference comes from the structure holding the waiting vertices.

    12. Tries and disjoint sets

    A trie, or prefix tree, stores strings along paths rather than inside nodes. Each edge carries one character, so a word is spelled out by walking down from the root, and a flag on the final node records that a real word ends there. Insert car, cat, cap, do, dog:

    Find "cat"root → c → a → t, then check the end-of-word flag = 3 steps
    Find "ca"reaches the a node, but its flag is not set → "ca" is a prefix, not a stored word
    CostO(L) for a word of length L — and L only. The number of words stored never enters the calculation.

    That independence is what makes a trie worth its memory. A hash table also finds a word in roughly constant time, but it cannot answer "what starts with ca?" — hashing deliberately destroys the relationship between "ca" and "cat". In the trie you walk to the a node and every word beneath it is a completion: car, cat, cap. That is autocomplete, and it is also how a router performs longest-prefix matching on an IP address.

    The price is space — a node may need a slot for every letter in the alphabet, so up to O(alphabet × nodes). Compressed variants such as radix trees merge chains of single-child nodes to claw some of it back.

    A disjoint set (union-find) maintains a partition under two operations: find(x) returns the representative of x's set; union(x, y) merges two sets. Two optimisations make it near-constant time:

    • Union by rank/size — attach the shorter tree under the taller one, keeping height O(log n).
    • Path compression — during find, re-point every node on the path directly at the root.

    Together they give an amortised cost of O(α(n)), where α is the inverse Ackermann function and is at most 4 for any input that fits in a computer. This is the structure that makes Kruskal's cycle test cheap.

    C — binary search, iterative and recursive
    int binaryIter(int A[], int n, int key) {
    int low = 0, high = n - 1;
    while (low <= high) {
        int mid = low + (high - low) / 2;   /* avoids (low+high) overflow */
        if (A[mid] == key)      return mid;
        else if (A[mid] < key)  low  = mid + 1;
        else                    high = mid - 1;
    }
    return -1;

int binaryRec(int A[], int low, int high, int key) {
    if (low > high) return -1;
    int mid = low + (high - low) / 2;
    if (A[mid] == key)     return mid;
    if (A[mid] < key)      return binaryRec(A, mid + 1, high, key);
    return binaryRec(A, low, mid - 1, key);
}

    Rotated sorted array. At every step one of the two halves is still sorted: compare A[low] with A[mid] to find which, test whether the key lies inside that sorted half, and recurse into it. Still O(log n).

    Which one to choose — the reasoning an examiner wants
    • Nearly sorted, small n → insertion sort. Adaptive, stable, O(n) on nearly-sorted input, tiny constant factor.
    • Guaranteed O(n log n) needed → merge sort (stable, needs O(n) space) or heap sort (in-place, unstable).
    • Fastest in practice, average case → quick sort. Its constant factor and cache behaviour beat merge sort despite the O(n²) worst case.
    • Linked list → merge sort. No random access is needed and merging costs no extra memory for links.
    • External / does not fit in RAM → external merge sort, because it reads and writes sequentially.
    • Small integer keys in a known range → counting or radix sort, beating the Ω(n log n) bound because they never compare keys.
    • Stability required (sorting by second key) → merge, insertion, bubble, counting or radix. Never quick, heap or selection.
    Quick sort's worst case

    Occurs when the pivot is always the smallest or largest element — with last-element pivoting that means the input is already sorted or reverse-sorted. Partitions are then of size n−1 and 0, giving T(n) = T(n−1) + O(n) = O(n²). Cures: random pivot, median-of-three pivot, or introsort (switch to heap sort once recursion goes too deep).

    C — Lomuto partition and quick sort
    /* Lomuto scheme: pivot is the last element */
int partition(int A[], int low, int high) {
    int pivot = A[high];
    int i = low - 1;                 /* boundary of the "<= pivot" region */
    for (int j = low; j < high; j++) {
        if (A[j] <= pivot) {
            i++;
            swap(&A[i], &A[j]);
        }
    }
    swap(&A[i + 1], &A[high]);       /* put the pivot in its final place */
    return i + 1;
}

void quickSort(int A[], int low, int high) {
    if (low < high) {
        int p = partition(A, low, high);
        quickSort(A, low, p - 1);    /* pivot itself is already correct */
        quickSort(A, p + 1, high);
    }
}

    15. The comparison-sort lower bound

    This is the one genuinely surprising result in the subject: it says that no future algorithm anyone invents can beat n log n by comparing elements. Not that nobody has found one — that none can exist. The argument is short enough to reconstruct, and easiest to see on three elements.

    Sorting three items, drawn as a tree of decisions

    An algorithm that only compares pairs has no other source of information. Every decision it makes is the answer to one yes/no question, so its entire behaviour can be drawn as a binary tree — comparisons at the internal nodes, and at each leaf the arrangement it has concluded:

    Two observations do all the work:

    1. The tree must have at least n! leaves

      Each distinct input ordering needs its own leaf, because the algorithm must produce a different rearrangement for each. Miss one and there is an input the algorithm sorts incorrectly. For n = 3 that is 6 leaves.

    2. A binary tree with L leaves has height ≥ log₂L

      Each comparison has two outcomes, so the leaves can at most double per level. Height h therefore permits at most 2ʰ leaves — and we need n! of them.

      Require2ʰ ≥ n! → h ≥ log₂(n!)
      n = 3h ≥ log₂6 = 2.58 → at least 3 comparisons — which is what the tree above shows
      Stirlinglog₂(n!) = Θ(n log n)
      Thereforethe height — and so the worst-case comparison count — is Ω(n log n)
    Every comparison-based sort needs Ω(n log n) comparisons in the worst case.
    This is why merge sort and heap sort are not merely good, they are optimal — their O(n log n) meets the bound exactly, so no comparison sort can ever be asymptotically faster. It also tells you where to look if you need more speed: not at a cleverer comparison strategy, but at avoiding comparisons altogether.

    Counting, radix and bucket sort beat this only because they never compare two keys — they use the key's value as an index, which costs them generality and extra space.

    Why negative weights break it. Dijkstra finalises a vertex the moment it becomes the closest unvisited one, and never revisits it.     Floyd's cycle detection (tortoise and hare)

    1. Start two pointers at the head. Move slow one node per step and fast two nodes per step.
    2. If fast or fast->next becomes NULL, the list ends — there is no cycle.
    3. If slow == fast at any point, a cycle exists.
    4. To find the start of the cycle, reset slow to the head and advance both one step at a time; they meet at the first node of the cycle.

    Why it must terminate. Suppose the list has a tail of μ nodes leading into a cycle of length L. After at most μ steps both pointers are inside the cycle. From then on, each step increases fast's position by 2 and slow's by 1, so the gap between them closes by exactly 1 per step (modulo L). A gap of at most L − 1 shrinking by 1 each step reaches 0 within L further steps. Total steps ≤ μ + L ≤ n, so the algorithm is O(n) with O(1) extra space — strictly better than the hash-set method, which also runs in O(n) time but needs O(n) space.
